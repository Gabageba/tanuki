# Коммит → push → PR

Подсказка от пользователя: `$ARGUMENTS`

Весь диалог — на русском, сообщения коммитов и PR — на английском.

## 1. Ревью

Запусти скилл `review` через `Skill`. Он починит механику и переводы и вернёт сводку.

- Есть пункты «Нужно решение» — **не коммить**. Покажи сводку и спроси через
  `AskUserQuestion`: «Починить» (Recommended) / «Коммитить как есть» / «Остановиться».
  «Починить» — исправь, затем снова `review` с начала. «Коммитить как есть» — продолжай.
- `pnpm lint` красный после ревью — не коммить, покажи, что упало.

## 2. Ветка

`git branch --show-current`. На `master` не коммить: создай ветку `feat/<суть-kebab>` (`fix/`,
`docs/`, `chore/` по типу изменений) и переключись на неё — `git switch -c`. Изменения
переедут вместе с рабочей копией.

## 3. Разбиение на коммиты

Посмотри всё: `git status --porcelain`, `git diff HEAD`, новые файлы. Сбрось индекс
(`git reset -q`) и разбей изменения на логичные коммиты **по файлам** (без частичных hunk-ов).
Ориентир — история репозитория (`git log --oneline -20`):

- `docs: …` — изменения в `docs/` отдельным коммитом;
- `feat(web): playground for …` — страница песочницы отдельно от реализации;
- `chore(Codex): …` — `AGENTS.md`, `.Codex/`;
- `chore: …` — тулинг и конфиги корня;
- реализация — `feat(web)`, `feat(api)`, `fix(parsers)`, …; если фича одна и задевает web и
  api, это один `feat: …` без scope;
- тесты идут в коммит с кодом, который они проверяют; ключи `ru.json`/`en.json` — в коммит с
  кодом, который их использует.

Мелкие изменения одной темы — один коммит; не дроби ради дробления. Порядок — чтобы каждый
коммит по отдельности собирался (контракты → api → web → docs).

Сообщение: conventional commits (проверяет commitlint), `type(scope): summary` в нижнем
регистре, повелительное/назывное, без точки, ≤ 72 символов. Подсказку из `$ARGUMENTS` учти.
Тело — только если summary не объясняет зачем. **Никаких `Co-Authored-By` и «Generated with
Codex»** — ни в коммитах, ни в PR.

Подтверждения не спрашивай — коммить сразу.

## 4. Коммиты

Для каждой группы: `git add <файлы>` → `git commit -m "<сообщение>"`.

Хук `pre-commit` запускает lint-staged (eslint, stylelint, prettier, `lint:i18n`) и
`turbo typecheck test`; `commit-msg` — commitlint.

- Хук упал — коммит **не создан**. Разберись по выводу, почини, `git add`, повтори тот же
  `git commit`. Не используй `--no-verify` и `--amend`.
- Падает typecheck/тест из-за того, что нужный файл попал в следующую группу, — перегруппируй.
- Не можешь починить однозначно — остановись и покажи ошибку.

В конце `git status` должен быть чистым (кроме того, что в `.gitignore`).

## 5. Push

`git push -u origin HEAD`. Отказ (non-fast-forward) — не форсить: покажи, что произошло, и
спроси.

## 6. PR

`gh pr view --json url,state,title,body 2>/dev/null`:

- нет PR (или он закрыт/смёржен) — `gh pr create --base master --title "<title>" --body "<body>"`:
  - title — conventional, как главный коммит ветки (`feat(web): account menu`);
  - body — 2–5 пунктов: что сделано и где решение (`docs/11-ui-decisions.md`, если есть).
- открытый PR уже есть — не создавай новый, а обнови его под всю ветку
  (`git log --oneline master..HEAD`):
  - title — пересобери по тем же правилам из всех коммитов ветки. Если новые коммиты
    расширили суть (задели ещё и api → scope уходит, добавилась вторая фича) — поменяй; если
    title и так её описывает — оставь как есть;
  - body — допиши в конец пункты о том, что добавили коммиты этого запуска, в том же стиле,
    что уже есть. Существующий текст не переписывай и не удаляй (его мог править
    пользователь); пункт, который уже покрывает новое, не дублируй — уточни его, если нужно;
  - `gh pr edit --title "<title>" --body-file <файл в scratchpad>` (body через файл — без
    проблем с кавычками и переносами). Если ничего не поменялось — не вызывай.

## 7. Итог

Коротко: ветка; список коммитов (`git log --oneline master..HEAD`); что починил ревью;
что осталось «На заметку» или закоммичено как есть по решению пользователя; ссылка на PR
(и создан он или обновлён — что поменялось в title/body).
