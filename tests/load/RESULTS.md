# Стресс-тест 12 ноября 2026 г.

## После ограничения кеша и изображений

Повторный тест выполнен на одном CPU с бюджетом 768 МиБ для пяти контейнеров
(ещё 256 МиБ оставлено для ОС). Кеш отделён от счётчиков защиты входа,
ограничен 32 МиБ с LRU-вытеснением. Предел загрузок — 8, преобразований обложек — 1.

| Сценарий                                                  | Память всего стека | Результат                                   |
| --------------------------------------------------------- | -----------------: | ------------------------------------------- |
| 100 одновременных загрузок страниц                        |            268 МиБ | 956 запросов, без ошибок и OOM              |
| 200 одновременных загрузок страниц                        |            289 МиБ | 220 успешных ответов, 41 ответ 429; OOM нет |
| 25 одновременных обработок новых обложек                  |            271 МиБ | 127 успешных ответов, 2 ответа 429; OOM нет |
| 50 одновременных обработок новых обложек                  |            250 МиБ | 43 успешных ответа, 26 ответов 429; OOM нет |
| 10 одновременных обработок новых обложек в течение минуты |            283 МиБ | 539 запросов, без ошибок; p95 1194 мс       |

В минутном тесте кеш сохранил предел: 31,8 МиБ данных, 378 вытесненных ключей.
Отдельная проверка записала в кеш 64 МиБ данных, подтвердила вытеснение и сохранность
счётчика rate limit. После перезапуска API старый namespace `cache:*` был удалён,
а счётчик `ratelimit:*` остался. Большое тело, переполнение при распаковке gzip и
чрезмерный ресайз отвергнуты; API сохранил readiness.

Все пять сервисов остались запущены. При перегрузке ограничение возвращает 429
с `Retry-After`, а не допускает неограниченное накопление изображений в памяти.
HTTP 429 — отказ части работы, его нельзя считать успешным выполнением всех запросов.
Сырые данные — `report/1gib-with-limits.json`, параметры — [ограничения ресурсов](../../docs/14-resource-limits.md).

## Исходный тест до ограничений

Ниже сохранён предыдущий прогон API с оптимизацией Sentry/Swagger, до ограничения
кеша и изображений. Четыре сервиса закреплены за одним CPU Docker на локальном ARM64-хосте.
Использованы первоначальные бюджеты из исходных JSON-отчётов,
200 тестовых аккаунтов и настоящая авторизация, PostgreSQL, Valkey, Caddy, HTML-парсер AComics,
Sharp и Argon2. Внешние сайты заменены локальным источником. Swap отключён.

Это короткие ступени насыщения по 12 секунд, а не проверка стабильности в течение суток.
Память ниже — одновременная сумма четырёх контейнеров без ОС, генератора и локального источника.
Измерение раз в ~500 мс может пропустить короткий пик перед OOM.

Дополнительно профиль 1 ГиБ проверен в течение 60 секунд с 50 одновременными загрузками
страниц: 5300 запросов, ошибок нет, 87,6 страницы/с, p95 753 мс, пик памяти 440 МиБ.
Это проверка одной устойчивой ступени; она не заменяет длительный тест на утечки.
Всего в завершённых прогонах выполнено 65 003 запроса, включая неудачные ступени.

## Найденные ограничения

1. Прокси собирает страницу целиком в памяти (`streamToBuffer`), поэтому одновременные
   загрузки крупных страниц увеличивают память API. 100 загрузок привели к OOM именно
   контейнера с лимитом 448 МиБ. Это не доказывает, что вся машина с 1 ГиБ исчерпала RAM:
   сервисы не могут занять свободную часть лимита другого контейнера.
2. Кеш обложек не ограничен по размеру. На профиле 1 ГиБ Valkey достиг 64 МиБ и был завершён.
   Ошибка кеша деградирует в прямые запросы, поэтому ответы ещё могли быть 200, хотя
   readiness уже перестал проходить. Увеличение RAM откладывает проблему, но не ограничивает кеш.
3. На одном CPU обработка новых тяжёлых обложек ограничилась примерно 9 обложками/с.
   Дополнительная RAM не устраняет очередь и таймауты при 50 одновременных обработках.

Эти ограничения устранены отдельным кешем с LRU и ограничением параллельных загрузок/
перекодирований, как описано в повторном прогоне выше. Исходный кеш делил Valkey
со счётчиками rate limit: включение вытеснения в общем хранилище затронуло бы защиту входа.

## Границы вывода

Конфигурация 4 ГиБ для личного использования по этим данным не требуется. Профиль 1 ГиБ
с введёнными ограничениями справился с проверенными сценариями; 2 ГиБ дают дополнительный
запас. Это не гарантия для произвольных библиотек, размеров изображений и типов нагрузки.

Не измерялись длительное накопление кеша, большая пользовательская библиотека, фоновые
проверки, поиск по всем источникам, особенности декодирования других источников, резервное
копирование, сборка образов и память браузера. Число запросов не равно числу читателей.
Локальная сеть не ограничивалась по пропускной способности; цифры запросов/с не являются
гарантией для CPU и сети произвольного VPS. Полноценная виртуальная машина с 1/2 ГиБ не запускалась.

Исходные данные текущего прогона сохранены в игнорируемом `report/`: `1gib-ramp.json`,
`1gib-login.json`, `1gib-combined.json`, `1gib-soak.json`, `2gib-ramp.json`, `combined-results.json`.
Повторный запуск может заменить
`report/results.json`; команды воспроизведения приведены в README.
