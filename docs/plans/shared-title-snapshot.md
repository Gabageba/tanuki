# Общий снимок тайтла

Статус: **Реализован** · 2026-11-11

Задача: `shared-title-snapshot` · будущая ветка `feat/shared-title-snapshot`.
Макеты и маршрут песочницы не нужны: интерфейс остаётся прежним.

## Зачем

Сейчас название, обложка, возрастной рейтинг и тип тайтла дублируются в строках
`bookmarks` и `reading_progress`. У каждого пользователя остаётся своя версия,
которая может годами не меняться после добавления закладки или последнего чтения.
Крон получает свежие детали того же тайтла, но карточки остальных пользователей
эти метаданные не используют.

Нужен один общий снимок **тайтла на конкретном источнике**, определяемый
`titleKey = linkKeyOf(sourceId, url)`. После получения деталей источника следующий
запрос любого пользователя использует общий снимок. Подтверждённые совпадения
между источниками продолжают объединять закладки и прогресс, но не объединяют
разные названия и обложки в один снимок на всю группу.

Успех: изменение названия, обложки, рейтинга или типа на источнике попадает в
закладки и «Продолжить чтение» всех пользователей через обычные пути обновления;
резервная копия одного пользователя не меняет чужие карточки. Папки, отметки,
прочитанные главы, статистика и правила новых глав сохраняются.

## Скоуп

- **Входит одним этапом:** общие метаданные закладок и прогресса; миграция существующих
  данных; все пути записи и чтения, включая импорт с источников, восстановление,
  экспорт резервной копии и «Вернуть закладку»; дозаполнение и чистка снимков;
  тесты и документация.
- **Входит:** личный запасной снимок для данных из файла и старых записей,
  происхождение которых неизвестно. Он нужен только до появления общего снимка
  от источника и не становится вторым постоянным хранилищем метаданных.
- **Не входит:** новые страницы, кнопки обновления, настройки, статусы свежести,
  тосты об изменении обложки, новые SSE-события и изменения дизайна карточек.
- **Не входит:** регулярный опрос всех тайтлов из прогресса; массовая загрузка
  метаданных всего каталога; изменение формата или версии файла резервной копии.
- **Потом:** отдельные продуктовые расширения не запланированы. Реализацию можно
  разбить на технические шаги, но результат задачи охватывает весь переход.

## Сценарии

### Изменение метаданных на источнике

1. Пользователь добавляет тайтл в закладки или начинает читать. Сервер получает
   детали источника и сохраняет общий снимок; личная строка хранит состояние пользователя.
2. Источник меняет название, обложку, рейтинг или тип.
3. Крон отслеживаемых закладок либо обычное открытие тайтла / чтение получает
   обновлённые детали и обновляет общий снимок этого `titleKey`.
4. При следующем запросе закладок или «Продолжить чтение» пользователи получают
   новые метаданные. Уже открытая страница не обязана меняться мгновенно.

### Тайтл есть только в прогрессе

1. Пользователь читает тайтл без закладки; сохраняются прогресс и общий снимок.
2. Регулярного дополнительного опроса для такого тайтла нет. Если его отслеживает
   кто-то другой, существующий крон обновляет общий снимок для всех.
3. Иначе снимок обновляется при следующем открытии тайтла или чтении.
   Просмотр главной сам по себе не перепроверяет уже известные метаданные по возрасту.
4. Для старой строки вообще без пригодного снимка сохраняется дозаполнение из
   источника при выдаче «Продолжить чтение»; это восстановление отсутствующих данных,
   а не регулярная проверка свежести.

### Восстановление резервной копии

1. «Профиль → Данные → Восстановить из копии»: существующая сводка и вопросы.
2. Сервер восстанавливает папки, закладки и прогресс по прежним политикам.
3. Общий снимок от источника уже есть — данные файла его не меняют.
4. Общего снимка ещё нет — метаданные файла сохраняются как личный запасной
   снимок восстановившего пользователя. Его карточки и последующий экспорт
   могут использовать эти данные; другие пользователи их не получают.
5. Первый подходящий ответ источника создаёт общий снимок. Он получает приоритет,
   личный запасной снимок становится не нужен и удаляется.
6. Если источник недоступен, восстановление всё равно завершается; личные данные
   не теряются и не публикуются. Новых шагов модалки или подтверждений нет.

### Связанные тайтлы

1. Закладка добавлена на MangaLib, затем пользователь читает подтверждённую копию
   на ReManga. Существующее правило выбирает источник назначения карточки.
2. Название, обложка, рейтинг и тип берутся из снимка **этого назначения**.
   Сам факт наличия строки закладки на ReManga больше не определяет источник метаданных.
3. Недоступность источника не удаляет его последний известный снимок. Если прежние
   правила выбора доступной цели переключают карточку на другую копию, её метаданные
   переключаются вместе с целью.

### Миграция и отмена удаления

1. После перехода пользователь видит свои старые метаданные до ответа источника.
2. Удаление закладки и «Вернуть закладку» работают как прежде, с проверкой папки
   и соответствия ключа тайтлу. Возвращается личное состояние, а не прежняя версия
   общих метаданных поверх более свежей.
3. Если источника и общего снимка нет, допустимые данные возврата остаются личным
   запасным снимком. Сохраняется существующее ограничение: при недоступном источнике
   обложка из клиентского payload возврата не становится доверенной обложкой прокси.

## Логика и правила

### Что общее и что личное

- Общий снимок содержит только метаданные тайтла от источника и идентификаторы.
  Он не содержит владельца, папку, прогресс, покупки, сессию источника или другие
  сведения из личного аккаунта.
- Папка, даты добавления и визита, скрытие из «Продолжить чтение», глава, ветка,
  страница и время чтения остаются личными. Снимок номера и названия **главы**
  в прогрессе сохраняется: он нужен для выравнивания отметок между источниками.
- Права не меняются: приложение требует вход, обычные пользователи и персонал
  используют одинаковые правила снимков. Прямого редактирования общего снимка нет.
- Для каждой карточки выбирается один целостный снимок: общий от источника,
  иначе личный запасной того же `titleKey`. Не смешиваем название одного источника
  с обложкой другого или рейтинг из файла с названием общего снимка.

### Приоритет записей

| Данные                                                                        | Правило                                                                                                            |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Успешные детали источника                                                     | Создают или обновляют общий снимок; имеют приоритет над списком закладок источника и любыми личными данными        |
| Список закладок, полученный сервером непосредственно от источника при импорте | Может создать начальный общий снимок; не заменяет уже полученные полные детали неполной строкой списка             |
| Резервная копия                                                               | Никогда не пишет метаданные в общую таблицу; при отсутствии общего снимка создаёт личный запасной                  |
| Старые личные записи при миграции                                             | Сохраняются только как личные запасные; дата пользовательской записи не доказывает достоверность метаданных        |
| Payload «Вернуть закладку»                                                    | Не перезаписывает общий снимок; сервер предпочитает детали источника и соблюдает существующие ограничения возврата |
| Ошибка источника или stale-fallback кеша                                      | Не стирает метаданные и не выдаётся за новую удачную проверку                                                      |

Происхождение общего снимка — внутреннее понятие API. Предлагаемый const в
`apps/api/src/library/models.ts`, тип через `EnumLiteralsOf` из `@tanuki/contracts`:

```ts
export const TITLE_SNAPSHOT_ORIGIN = {
  SOURCE_DETAILS: 'sourceDetails',
  SOURCE_BOOKMARK: 'sourceBookmark',
} as const;
```

Приоритеты выражаются исчерпывающим `switch`, без таблицы соответствий.
Для записей одного происхождения старый ответ, завершившийся позже нового,
не должен откатывать метаданные. Нужна атомарная проверка времени получения
данных источника при upsert, а не только времени записи в БД.

Свежий ответ деталей может убрать обложку или изменить тип: известное отсутствие
значения заменяет старое. Неизвестный рейтинг или неполная строка импорта не должны
случайно снимать уже известный `ADULT`. Нормализация учитывает взрослый источник
и существующие правила доступа. Пользовательское подтверждение возраста остаётся личным.

### Свежесть

- Регулярный крон остаётся для отслеживаемых закладок: `BOOKMARK_UPDATES_CRON`,
  по умолчанию раз в три часа; источники в `down` пропускаются.
- Первые снимки закладок из любых папок по-прежнему дозаполняются существующей
  минутной задачей с лимитами, паузами и повторами. Наличие строки без метаданных
  или без первой проверки глав не должно ошибочно исключать её из дозаполнения.
- Для тайтлов только из прогресса нового периодического опроса нет.
- Открытие тайтла, получение глав и сохранение прогресса используют уже полученные
  детали для общего снимка. В частности, `CatalogService.getTitleDetails()`
  сейчас снимок не пишет — этот путь нужно добавить.
- Существующий кеш деталей сохраняется: свежий кеш можно использовать, обращение
  к источнику на каждую страницу чтения не требуется. Сейчас fresh TTL — 15 минут;
  fallback при сбое может быть старше. «Обновить при открытии» учитывает этот кеш.
- Обновления видны при следующем обычном запросе списков. Ни SSE-доставка метаданных,
  ни новый таймер опроса браузером не нужны. Свежий клиентский кеш может отобразиться
  сразу по прежним правилам; офлайн используется сохранённый ответ.

### Учёт глав отделён от наличия метаданных

Строка общего снимка, созданная из списка закладок источника, ещё не означает,
что сервер видел главы. Наличие строки и время обновления обложки не используются
как признак первой проверки глав.

- Ввести явный признак инициализации списка глав, например `chaptersInitialized`.
  Он выставляется при успешном получении списка, включая достоверно пустой список.
- Первый список помечает главы `baseline`, последующие сохраняют существующую
  семантику новых глав. Конкурентные первые записи сериализуются на `titleKey`.
- Ответ без списка глав не меняет число глав, не инициализирует список и не
  делает проверку глав свежей. Импорт из файла вообще не пишет в историю глав.
- Существующее ограничение записи глав раз в пять минут не блокирует обновление
  метаданных из более свежих деталей. Отдельно учитываются время метаданных
  и время попытки проверки глав.
- Платные главы не попадают в общий журнал. Сохраняются правила веток, визитов,
  числа глав, уведомлений и скрытия дочитанного из «Продолжить чтение».

## Данные и API

### Общая таблица

Расширить `title_chapter_snapshots`, не создавать вторую общую таблицу на тот же ключ:

| Поле                                                    | Назначение                                                                          |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `title_key`, `source_id`, `title_id`                    | Существующие ключ и идентификаторы источника                                        |
| `name`, `cover_url`, `content_rating`, `type`           | Общие метаданные; обложка — исходный URL, без подписи прокси                        |
| `metadata_origin`                                       | `sourceDetails` / `sourceBookmark`; null у старой строки только с состоянием глав   |
| `metadata_fetched_at`                                   | Когда источник отдал использованные метаданные; для сравнения конкурентных записей  |
| `chapters_initialized`                                  | Сервер уже получал первый список глав, независимо от наличия метаданных             |
| `checked_at`, `last_error`, `missing`, `chapters_count` | Существующее состояние проверки глав; `checked_at` допускает null до первой попытки |

Старые строки таблицы сохраняются, но без выдуманных названия и обложки: до первого
ответа источника личные запасные данные не становятся общими.

### Личный запасной снимок

Новая таблица `user_title_snapshot_fallbacks` с PK `(user_id, title_key)`:
`title_id`, `name`, `cover_url`, `content_rating`, `type` и время для детерминированного
выбора версии. У старого прогресса некоторые поля могут быть null. Пользователь
удаляется каскадно; чтение таблицы всегда ограничено текущим `user_id`.

При наличии одновременно старой закладки и прогресса одного пользователя на один
ключ выбирается наиболее свежий пригодный целостный снимок; при равенстве — закладка.
Время означает выбор между личными версиями, а не подтверждение источником.
При повторном восстановлении используются снимки тех записей, которые действительно
приняты текущими политиками восстановления; пропущенный конфликт не меняет запасные данные.

После появления пригодного общего снимка запасной больше не читается. Его можно
удалить в той же операции либо пакетной ночной чисткой; между этими действиями
пользователь уже видит общий снимок. После удаления общего снимка старый запасной
не должен внезапно воскресать.

Из `bookmarks` и `reading_progress` удалить дубли метаданных тайтла, включая
дублирующий `title_id`, после переноса и перевода всех потребителей. Идентификатор
для ответа берётся из общего или личного запасного снимка. `source_id` может
сохраниться как идентификатор строки прогресса/закладки; это не личная копия метаданных.

### Пути чтения и записи

- `TitleSnapshotsService` — общая точка нормализации, приоритетов и записи.
  Умеет работать внутри транзакции восстановления / импорта; не открывает
  независимую транзакцию, которая переживёт откат личных записей.
- `BookmarksService`, `bookmark-groups.ts`, `library/models.ts` — собирают строки
  с разрешённым снимком, включая цели только из прогресса. Поиск и сортировка
  используют имя, которое реально показано в карточке. Прочие потребители,
  в том числе конфликт папок и payload отмены удаления, получают метаданные тем же правилом.
- `ReadingProgressService` — пишет личную позицию и общий снимок из деталей;
  «Продолжить чтение» читает снимки пакетно. Не делает запрос к источнику для
  каждого уже известного тайтла. Старые строки без пригодного снимка дозаполняются
  прежним ограниченным потоком; при сбое такая карточка временно пропускается.
- `CatalogService` — обновление из деталей и списка глав. Сбой необязательной
  записи снимка не ломает выдачу тайтла; сохранение личного состояния при сбое
  БД по-прежнему сообщает ошибку, а не ложный успех.
- `LibraryMergeService`, `BackupRestoreService` — запись личного состояния и
  запасных снимков одной транзакцией, с существующей блокировкой на пользователя.
  Разные пользователи, восстанавливающие один тайтл, не меняют данные друг друга.
- `SourceImportService` — происхождение данных не теряется при использовании
  общей механики merge: ответ сайта может создать общий снимок, файл — нет.
  `SourceImportProgressService` использует полученные детали для общего снимка,
  даже если политика прогресса оставила более дальнюю личную отметку.
- `BackupExportService` — собирает прежние поля файла из общего снимка, иначе
  личного запасного. Экспорт не обращается к источникам и не теряет недоступные
  тайтлы. Поля nullable у старого прогресса остаются допустимыми по прежней схеме.
- `ParsersClientService` / `CacheService` — передают внутреннее время получения
  деталей из envelope кеша, чтобы cache hit не выдавался за новый ответ источника.
  Stale-fallback не откатывает общий снимок и не продлевает успешную проверку.

Новых публичных эндпоинтов и полей ответов нет. Сохраняются формы `BookmarkItem`,
`BookmarkRow`, `ContinueReadingItem`, запросов прогресса и `Backup`.
В `packages/contracts/src/reading-progress.ts` обновляется комментарий о происхождении
метаданных. Парсерам новые методы и поля не нужны: имеющихся `RawTitle` и `RawBookmark`
достаточно. Внутренние сведения кеша не попадают в контракт web.

Обложки по-прежнему подписываются при выдаче. Недоверенные адреса из личного
запасного снимка не становятся основанием подписать произвольный внешний URL:
нужна проверка допустимости для соответствующего источника; неподтверждённую
обложку при невозможности проверки не показываем. Это не мешает восстановить
название и личное состояние. Ограничения img-прокси сохраняются.

### Миграция и жизненный цикл

1. Добавить поля общей таблицы и таблицу личных запасных снимков.
2. Перенести данные старых закладок и прогресса в личные запасные без сетевых
   запросов. Не выбирать «самую свежую запись любого пользователя» как общую.
3. Сохранить существующий журнал глав, даты `first_seen_at`, `baseline`, состояния
   ошибок и пользовательские даты. Признак инициализации вывести из имеющихся
   свидетельств: записанные главы или известное число, включая ноль. Строка только
   после ошибки либо без свидетельств списка остаётся неинициализированной.
4. Переключить все потребители на общее разрешение снимка и удалить прежние колонки.
   Миграция и новая версия API выкатываются согласованно, без параллельных старых
   писателей. Перед удалением колонок проверить полноту переноса на копии БД.
5. Общие метаданные заполняются обычными запросами и существующим дозаполнением
   закладок. Отдельного обязательного полного обхода источников при запуске нет.
6. Ночная чистка сохраняет общий снимок, пока хотя бы у одного пользователя есть
   закладка или прогресс этого `titleKey`, включая скрытый прогресс. Удаляет
   ненужные личные запасные, а затем осиротевшие общие снимки и журнал глав.
7. Удаление последней ссылки, восстановление и чистка согласуются транзакционно:
   конкурентная операция не должна оставить личную запись без обоих видов снимка
   либо стереть новую базовую историю глав. Нужны проверки на настоящем PostgreSQL.

## Крайние случаи

| Случай                                        | Что видит пользователь / правило                                                                                          |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Источник временно недоступен                  | Последний общий снимок, иначе свой запасной; чужой запасной не используется                                               |
| Тайтл удалён с источника                      | Название и обложка сохраняются; доступность и выбор резервной цели работают по прежним правилам                           |
| Снимка вообще нет, источник не ответил        | Старый прогресс остаётся, карточка «Продолжить чтение» временно пропускается, как сейчас                                  |
| Изменился рейтинг на 18+                      | Следующий ответ использует новый рейтинг; действуют существующие настройки скрытия и блюра                                |
| Файл подменяет название или рейтинг           | Влияет только на личный запасной снимок загрузившего; общий снимок не меняется                                            |
| Источник явно убрал обложку                   | Карточка без обложки по существующему варианту; старый запасной URL не подставляется                                      |
| У источника нет типа или данных о рейтинге    | Используется нормализация; неполный ответ не снимает известный 18+ по умолчанию SAFE                                      |
| 0, 1 или много глав                           | Сохраняются нынешние подписи, счётчики и ветки; ноль отличается от непроверенного списка                                  |
| Сначала появился снимок без глав              | Первая реальная выдача глав остаётся базовой и не создаёт ложные новые главы                                              |
| Два первых запроса или импорт одновременно    | Одна общая версия и одна инициализация глав; личные состояния не смешиваются                                              |
| Старый ответ пришёл позже нового              | Он не откатывает общий снимок                                                                                             |
| Длинное название, обложки нет, тип неизвестен | Существующая карточка и её ограничения текста, без нового оформления                                                      |
| Пустые закладки или прогресс                  | Существующий EmptyState / скрытый блок, никаких дополнительных запросов метаданных                                        |
| Новая загрузка, фильтр, сортировка, страница  | Существующие скелетоны через PageLayout.Content / QueryBlock; никаких новых спиннеров и оверлеев                          |
| Ошибка основного запроса / блока              | Существующая обработка: QueryError у страницы, глобальное уведомление и пустое состояние у блока                          |
| Офлайн PWA                                    | Сохранённые ответы и метаданные скачанных глав; новые серверные метаданные появятся после сетевого запроса                |
| Прогресс накопился офлайн                     | Существующая очередь отправки; общий снимок обновляется после получения деталей сервером                                  |
| Гость / истекла сессия                        | Существующий вход; нового публичного доступа к библиотеке или запасным снимкам нет                                        |
| Большой импорт или миграция                   | Пакетные операции, дедупликация ключей, существующие лимиты запросов к сайтам; без запроса деталей на каждую строку файла |

## Дизайн

Используются существующие `BookmarkCard`, общая карточка `TitleCard`, карточки
главной и модалка `RestoreBackupModal`. Точки входа, последовательности действий,
мобильный и десктопный вид, светлая и тёмная темы остаются прежними.

Новых модалок нет, тон существующих не меняется. Понятия «общий снимок» и «личный
запасной снимок» — технические, в интерфейсе их не показываем. Пользовательские
термины остаются «Закладки», «Продолжить чтение», «Резервная копия».

Новых визуальных развилок, референсов и вопросов к макетам нет. Проверяем результат
на существующих состояниях Storybook; отдельный `/playground` для задачи не нужен.

## Этапы реализации

1. **Схема и миграция.** Изменения `schema.ts`, миграции в `apps/api/drizzle/`,
   модели снимков и перенос старых данных. Проверка на копии БД с конфликтующими
   личными версиями и недоступными источниками; сетевые запросы при миграции не нужны.
2. **Общая логика и кеш.** Разрешение общего/личного снимка, приоритеты, время
   получения деталей, атомарные upsert и независимая инициализация глав.
3. **Основные пути API.** Catalog, Bookmarks, ReadingProgress, группировка,
   крон и дозаполнение. Пакетное чтение снимков без N+1; сохранение прежних
   публичных контрактов и подписывания обложек.
4. **Перенос библиотеки.** Merge, восстановление, экспорт, импорт источников,
   достройка прогресса и возврат удалённой закладки. Передать происхождение данных
   явно; сохранить транзакции, политики конфликтов и блокировки пользователя.
5. **Чистка и завершение переноса.** Удалить прежние колонки после проверки
   всех потребителей; проверить удаление аккаунта, отсутствие потерь и гонки чистки.
6. **Проверки web и docs.** Не менять интерфейс и API-кеш PWA. При необходимости
   обновить только комментарии и фикстуры, завязанные на старое хранение. Документация
   отражает новую модель и отличие от исходного правила TODO.

Все этапы выполняются без макетов. Разделение на этапы — порядок разработки,
а не отдельные продуктовые поставки «сначала только закладки».

### Проверки и критерии приёмки

- Один свежий ответ источника меняет метаданные в следующих выдачах закладок
  и «Продолжить чтение» двух разных пользователей; их папки и прогресс не меняются.
- Карточка связанной группы использует метаданные источника назначения, в том
  числе когда там есть только прогресс, а строки закладки нет. Поиск и сортировка
  соответствуют показанному имени.
- Изменение на 18+, отсутствие обложки и неизвестный тип обрабатываются корректно
  в обычной карточке и в варианте без обложки.
- Поддельная копия при пустой общей таблице не влияет на другого пользователя;
  два пользователя могут иметь разные личные запасные данные одного ключа.
  После ответа источника оба видят общий снимок, запасные удаляются.
- Импорт с сайта и импорт файла идут через общий merge без смешения доверия;
  неполный список сайта не затирает полные детали.
- Проверить round-trip старой резервной копии: восстановление → экспорт →
  восстановление, включая недоступный источник, только прогресс, пустые nullable
  метаданные и конфликты пользовательских политик. Формат и версия прежние.
- Миграция сохраняет число личных записей, папки, даты, скрытие, страницы,
  статистику и журнал глав. Удаление колонок не оставляет читающих их потребителей.
- Базовый список, пустой базовый список, метаданные без списка, повторная проверка,
  404, платные главы, гонка первых запросов и stale-fallback не создают ложных новых глав.
- Чистка сохраняет снимок для прогресса без закладки и для скрытой отметки,
  удаляет настоящие сироты и ненужные запасные; гонка с восстановлением не теряет данные.
- Лента с известными снимками не начинает обход источников; крон не расширяется
  до всех отметок чтения. Запросы снимков пакетные, импорт учитывает существующие лимиты.
- Офлайн-очередь прогресса, скачанные главы и кешированные ответы продолжают работать;
  новые серверные метаданные не требуют мгновенной доставки в открытую вкладку.

Проверки: целевые Vitest-тесты API, интеграционные тесты миграции и конкуренции
на PostgreSQL, `pnpm --filter @tanuki/api typecheck` и lint затронутых файлов.
Web typecheck и существующие проверки PWA / Storybook запускаются по затронутым
путям и рискам; новые тесты не должны дублировать простое присваивание полей.

## Открытые вопросы

Пользовательских развилок не осталось. Имена новых колонок и организация
внутренних методов могут уточняться при реализации с сохранением описанных
приоритетов, изоляции, совместимости и жизненного цикла.

## Отвергнутые идеи

- **Сначала только закладки:** выбран весь переход за один этап.
- **Делать первый общий снимок из файла, как предлагал TODO:** даже первая запись
  может подменить чужую карточку; выбран личный запасной снимок до ответа источника.
- **Общая самая свежая старая запись при миграции:** её дата не доказывает
  происхождение, поэтому старые данные остаются личными.
- **Проверить все источники до завершения миграции:** переход не должен зависеть
  от доступности сайтов; выбран перенос без сети с последующим обычным заполнением.
- **Регулярно опрашивать все тайтлы из прогресса:** лишний фоновый обход давно
  заброшенного чтения; выбрано обновление при открытии и чтении.
- **Перепроверять известные снимки при каждом открытии главной:** лента читает
  сохранённый снимок; дозаполнение нужно только при отсутствии пригодных данных.
- **Мгновенно менять уже открытые карточки через SSE:** достаточно следующей
  обычной загрузки списка.
- **Показывать обложку исходной закладки при переходе на другой источник:**
  метаданные должны соответствовать назначению карточки.
- **Постоянно хранить личные дубли поверх общего снимка:** запасные данные временные,
  при появлении общего снимка они уступают ему и удаляются.

## Итог реализации — 2026-11-11

- Миграция `0036_polite_mandroid` расширяет общую таблицу, переносит прежние личные
  версии в `user_title_snapshot_fallbacks`, проверяет полноту и удаляет дубли колонок.
  Сеть при переносе не используется. Миграцию и API нужно выкатывать согласованно;
  рабочая база в ходе разработки не мигрировалась.
- Метаданные разрешаются пакетно; общие детали имеют приоритет над списком сайта,
  личный файл никогда не пишет в общий снимок. Происхождение и время запроса источника
  проходят через кеш. Первый список глав и пятиминутный throttle независимы от метаданных.
- Запись снимков и библиотеки участвует в одной транзакции. Ночная чистка берёт
  исключительную блокировку жизненного цикла; писатели — совместную. Изменения одного
  ключа сериализуются ограниченным набором упорядоченных advisory-блокировок, чтобы
  большой импорт не исчерпывал память PostgreSQL для замков.
- Общее и личное хранилища читаются одним SQL-запросом на пакет, чтобы замена резерва
  ответом источника не создавала разрыва видимости. В метаданные попадают только их поля:
  служебная дата резерва не меняет даты закладки, чтения или экспорта.
- Неподтверждённые CDN-адреса из личного резерва сохраняются для экспорта, но до ответа
  источника не подписываются для показа. Домены источника проверяются по каталогу.
- Проверено: 574 теста API (два существующих теста пропущены), в том числе 18 интеграционных
  сценариев на отдельной временной базе настоящего PostgreSQL с полной цепочкой миграций,
  конфликтующими старыми версиями, гонками, импортом, round-trip и набором из 1100 тайтлов.
  Также прошли API/web typecheck, 21 тест web (включая PWA) и lint изменённых файлов.
