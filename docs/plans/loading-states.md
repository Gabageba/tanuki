# Загрузка: единый механизм и поиск по мере ответов

Статус: **Реализован** · 2026-10-21
Задача: `loading-states` · ветка `feat/loading-states` · песочница `/playground/loading-states`

## Зачем

Загрузка сейчас нарисована по-разному в каждом месте. Около 30 компонентов сами проверяют
`isPending` / `isFetching` и решают, показать ли свой скелетон, поэтому:

- каталог и страница тайтла показывают скелетон на **любом** `isFetching`: вернулся во вкладку
  браузера — сетка мигнула скелетоном;
- закладки, управление и уведомления при смене фильтра или страницы держат старые данные
  (`keepPreviousData`) и никак не показывают, что идёт загрузка;
- в офлайне (PWA) запрос встаёт на паузу, и скелетон висит бесконечно;
- поиск ждёт самый медленный источник (до 5 с), хотя быстрые ответили за полсекунды.

Главный принцип: **устаревших данных пользователь не видит никогда** (кроме офлайна). Пока
что-то грузится, это видно. Что считать устаревшим, решает `staleTime` запроса: свежее из кэша
показывается сразу, устаревшее — нет, вместо него скелетон до ответа.

Концепция — когда скелетон, когда ничего, когда маленький `Loader` — уже решена и записана:
`docs/11-ui-decisions.md`, «Загрузка: скелетон или спиннер» → «Концепция 2026-10-21», правило
**Loading** в `CLAUDE.md`. Этот план — как её внедрить.

**Удача:** любой экран грузится одинаково и предсказуемо; блок не решает сам, когда рисовать
скелетон; на экране никогда нет устаревших данных без знака загрузки; свежий кэш показывается
мгновенно (назад в каталог — без загрузки и с прокруткой); результаты поиска появляются по мере
ответов источников.

**Остаётся как есть:** экран ошибки главного запроса в `PageLayout.Content`, пустое состояние и
глобальный тост при ошибке блока; маленькие `Loader` в контролах (кнопка, аватар, подгрузка
следующей порции, pull-to-refresh) и на экранах-процессах.

## Скоуп

- **Входит:**
  - **Этап 1.** Общий механизм загрузки: `skeleton` у `PageLayout.Content` и обёртка `QueryBlock`
    для блоков; задержка 200 мс при смене параметров и минимум 400 мс показа скелетона; прокрутка
    к началу блока; состояние «Нет соединения»; `staleTime` по умолчанию; перевод всех экранов
    на механизм.
  - **Этап 2.** Поиск по мере ответов: `GET /search` отдаёт поток SSE; секции на местах в порядке
    источников; «Нашлось на:» и «Не ответили» обновляются по ходу; «Повторить» перезапрашивает
    только не ответившие; общий дедлайн 15 с.
- **Потом:** прогрев кэша матчинга заранее, если первое открытие тайтла окажется заметно долгим.
- **Не входит:** матчинг по мере ответов (см. «Отвергнутые идеи»); офлайн-режим чтения и прочее
  из PWA-плана — здесь только то, что блок не висит в скелетоне без сети.

Этапы делаются в одной ветке по очереди; этап 1 можно смержить отдельно.

## Сценарии

1. **Переход на страницу.** Человек открывает каталог → сразу видит скелетон раскладки (строка
   источника, фильтры, сетка) → данные приходят → скелетон сменяется содержимым. Если в кэше
   свежие данные (не старше `staleTime`) — содержимое сразу, без запроса: назад со страницы
   тайтла в каталог — та же сетка и та же прокрутка. Если в кэше устаревшие — скелетон сразу,
   устаревшее не показывается ни на миг.
2. **Смена фильтра, сортировки, страницы, вкладки.** Человек меняет сортировку закладок →
   ~200 мс видна старая сетка без изменений → если ответ пришёл, сетка просто подменяется; если
   нет — на месте сетки скелетон, и он держится не меньше 400 мс → новая сетка. Если блок был
   прокручен вниз, его верх поднимается в видимую область.
3. **Возврат во вкладку браузера.** Человек вернулся в приложение через час → данные на экране
   устарели и перезапрашиваются → ~200 мс прежнее содержимое, потом скелетон (минимум 400 мс) →
   свежие данные. Бесконечный список при этом начинается сначала, блок прокручивается к началу.
   Если данные ещё свежие — ничего не происходит.
4. **Перезапрос после действия.** Человек переносит закладку в другую папку или удаляет
   уведомление → список перезапрашивается → ~200 мс старый список, потом скелетон → новый.
   Оптимистичных обновлений у списков нет — без скелетона карточка висела бы на месте, будто
   ничего не произошло.
5. **Нет сети.** Человек открывает уведомления в метро → запрос встаёт на паузу → на месте блока
   «Нет соединения» → сеть вернулась → запрос уходит сам, блок снова в скелетоне → лента.
   Если данные уже были на экране, они остаются.
6. **Поиск.** Человек ищет «Берсерк» → сразу скелетоны секций на местах его источников по
   порядку → ответил MangaLib — его секция встаёт на место, в шапке появляется чип «MangaLib» →
   Desu ничего не нашёл — его место схлопывается → Remanga не уложился в 15 с — его место
   схлопывается, внизу строка в «Не ответили» → «Повторить» → место Remanga снова скелетон →
   ответ встаёт на своё место; найденное у остальных не трогается.

## Логика и правила

### Что показывает обёртка

Решение принимает общий механизм по состоянию запроса TanStack Query:

| Состояние запроса                                                | Что на экране                                                           |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Нет данных, запрос идёт (`isPending`, `fetchStatus: 'fetching'`) | `skeleton` — сразу                                                      |
| Нет данных, запрос на паузе (`fetchStatus: 'paused'`, офлайн)    | «Нет соединения»                                                        |
| Нет данных, запрос упал                                          | страница — `QueryError`; блок — его пустое состояние (`empty`)          |
| Старые данные вместо новых (`isPlaceholderData`) меньше 200 мс   | старое содержимое как есть                                              |
| Старые данные вместо новых дольше 200 мс                         | `skeleton`, минимум 400 мс; верх блока прокручивается в видимую область |
| Устаревшие данные в кэше при монтировании, идёт запрос           | `skeleton` — сразу, устаревшее не показывается                          |
| Данные были на экране, начался перезапрос (фокус, мутация)       | то же, что смена параметров: 200 мс содержимое, потом `skeleton`        |
| Живые данные (`meta.live`), идёт перезапрос                      | содержимое как есть                                                     |
| Данные свежие (не старше `staleTime`) из кэша                    | содержимое сразу, запроса нет                                           |
| Данные есть                                                      | содержимое                                                              |

- **Смена параметров = `keepPreviousData`.** Чтобы работало правило «200 мс старого, потом
  скелетон», у каждого запроса с параметрами (фильтр, сортировка, страница, вкладка, поиск внутри
  списка) стоит `placeholderData: keepPreviousData`. Переход к другой сущности (другой тайтл,
  другой источник каталога, новый поисковый запрос) — это `key` по сущности на компоненте, как уже
  сделано у тайтла (`key={titleId}`) и поиска (`key={query}`): данных нет — скелетон сразу.
- **Минимум 400 мс** считается от появления скелетона; ответ, пришедший раньше, ждёт конца
  минимума. Константы — `SKELETON_DELAY_MS = 200`, `SKELETON_MIN_MS = 400` рядом с механизмом.
- **Прокрутка.** Только когда скелетон появился из-за смены параметров и верх блока выше видимой
  области. Учитывается липкая шапка (`scroll-margin-top`). При первой загрузке не прокручивается.
- **Любой перезапрос — скелетон.** Фокус вкладки, `invalidateQueries` после мутации, смена
  параметров — механизм не различает причины: идёт запрос за данными, значит показанное может
  быть устаревшим. Различает только, были ли данные на экране (тогда 200 мс задержки против
  мигания) или нет (тогда сразу).
- **Свежесть — `staleTime`.** Пока данные не старше `staleTime`, запросов нет и показ
  мгновенный. Умолчание `QueryClient` — 5 минут (сейчас 0: запрос на каждое монтирование и
  фокус); у запросов, где уже задан свой `staleTime`, он остаётся.
- **Живые данные — исключение.** Запросы, которые обновляются сами по таймеру
  (`refetchInterval`: «Здоровье источников», счётчик непрочитанных) или по SSE (лента
  уведомлений), помечаются `meta: { live: true }` — их перезапрос тихий: показанное актуально на
  момент последнего опроса.
- **Оптимистичное обновление — не перезапрос.** Мутация, обновившая кэш через `setQueryData`
  (переключатели и порядок в настройках, кнопка закладки на тайтле, прогресс чтения, история
  поиска), не инвалидирует его на успехе — иначе изменение, уже видное на экране, сменилось бы
  скелетоном. Нужен ответ сервера — кладётся в кэш через `setQueryData`. Инвалидация остаётся
  только на ошибке (откат).
- **Офлайн — исключение из принципа.** Без сети показываются данные из кэша, даже устаревшие;
  нет данных — «Нет соединения».
- **Ошибка перезапроса**, когда данные были на экране, — блок возвращает их (лучше устаревшее,
  чем пусто) и глобальный тост говорит об ошибке. Страница — так же, `QueryError` только без
  данных.
- **Что известно без запроса, рисуется сразу.** Вкладки настроек, строка источника, блоки, не
  ждущие запроса, стоят снаружи обёртки; `skeleton` описывает только то, что ждёт ответа.

### Поиск (этап 2)

- Порядок мест — порядок источников, который сервер присылает первым событием; до него —
  `SKELETON_SECTIONS` (3) мест.
- Источник ответил с результатами — секция на его месте. Ничего не нашёл — место исчезает.
  Ошибка, тайм-аут, закрыт, недоступен — место исчезает, источник появляется в «Не ответили».
- «Нашлось на:» — чип появляется, как только источник что-то нашёл.
- «Ничего не нашлось» (`NothingFound`) — только когда ответили все и ничего нет.
- «Повторить» — новый поток только по не ответившим (`sources=…`), с флагом повтора: в историю
  не пишется. Повторяемые источники уходят из «Не ответили» и становятся местами-скелетонами
  в своём порядке; найденное у остальных остаётся.
- Смена фильтров поиска — новый поток по общему правилу: 200 мс старой выдачи, потом скелетоны
  мест. Фильтры остаются на месте.
- Общий дедлайн веера — 15 с (`SEARCH_TIMEOUT_MS`, было 5 с): быстрые источники уже на экране,
  ожидание медленных больше ничего не стоит.

## Данные и API

### Этап 1 — только web

- `PageLayoutBaseQuery` (`shared/ui/PageLayout/models.ts`) дополняется `isPlaceholderData` и
  `fetchStatus` — их читает механизм. `mergePageQueries` сводит их по всем запросам страницы
  (placeholder — если хоть один, paused — если хоть один на паузе без данных).
- `keepPreviousData` добавляется запросам с параметрами, где его нет: каталог (`useCatalog`),
  подборки (`useSelectionsSection` — вариант блока), поиск. Уже есть: закладки, управление,
  уведомления, `useBookmarksLookup`.
- `QueryClient` (`app/Providers/QueryClientProvider.tsx`): `staleTime` по умолчанию 5 мин;
  `refetchOnWindowFocus` остаётся включённым. Тип `meta` расширяется полем `live` (через
  `Register` TanStack Query).
- Онлайн-статус — `onlineManager` TanStack Query (он и ставит запросы на паузу), своего
  `navigator.onLine` не заводим.

### Этап 2 — поиск потоком

```
GET /search?query=...&sources=...&types=...&states=...&limit=10[&retry=1]
    → text/event-stream
event: sources   data: { sourceIds: string[] }    — порядок мест, первым, сразу
event: group     data: SearchGroup                — по одному на источник, по готовности
event: done      data: {}                         — все источники ответили или вышел дедлайн
```

- Ответ JSON `SearchResponse` уходит — единственный потребитель `useSearch`. `SearchGroup` не
  меняется. Новые схемы в `packages/contracts/src/search.ts`: `SearchSourcesEventSchema`,
  `SEARCH_STREAM_EVENT` = `{ SOURCES: 'sources', GROUP: 'group', DONE: 'done' }`.
- Пропущенные источники (`locked`, `unavailable`) отдаются `group` сразу после `sources`.
- Дедлайн общий: в момент дедлайна все не ответившие уходят `group` со статусом `timeout`, затем
  `done`.
- Ошибка до начала потока (400 `searchQueryMissing`, 401) — обычный HTTP-ответ с ошибкой.
- `retry=1` — не писать в историю. Без него запись идёт параллельно вееру, как сейчас.
- Закрытие соединения клиентом (ушёл со страницы, сменил фильтр) — сервер перестаёт слать
  события; запросы к источникам доживают сами (как сейчас после дедлайна).
- Заголовки как у `/notifications/stream`: `X-Accel-Buffering: no`,
  `Cache-Control: no-cache, no-transform`.
- Клиент: `useSearch` на `streamedQuery` (TanStack Query 5.101): `fetch` с `AbortSignal`,
  разбор кадров SSE из `ReadableStream`, данные — `{ sourceIds, groups, isDone }`. Не
  `EventSource`: его нельзя отменить сигналом запроса и он не отдаёт HTTP-ошибку.
- Повтор: отдельный поток с `retry=1`, его группы вливаются в кэш основного запроса
  (`setQueryData`), повторяемые на время повтора убираются из групп.
- `SEARCH_TIMEOUT_MS` по умолчанию 15 000 (`apps/api/src/config/env.ts`).

## Дизайн

Новых экранов нет. Видимые изменения:

- скелетоны вместо мигания и молчаливого ожидания — в раскладке каждого блока, как уже есть;
- состояние «Нет соединения» — `EmptyState` в месте блока или страницы;
- поиск — секции заполняются по мере ответов.

Терминология:

| Понятие            | В UI                                                        |
| ------------------ | ----------------------------------------------------------- |
| Офлайн, данных нет | «Нет соединения» (`noConnection`)                           |
| Пояснение          | «Загрузится, когда появится сеть» (`willLoadWhenOnline`)    |
| Кнопка             | «Повторить загрузку» (`retryLoading`), `ArrowClockwiseIcon` |

- **«Нет соединения»** — `EmptyState` с кнопкой «Повторить загрузку» в `EmptyState.Actions`:
  запрос и так уйдёт сам при появлении сети, но кнопка даёт человеку проверить, не вернулась ли
  она (`onlineManager` в браузере ошибается: Wi-Fi без интернета считается онлайном).
- **Поиск:** секция встаёт на место скелетона мгновенно, без анимации; место ничего не нашедшего
  источника исчезает сразу. Места-скелетоны одинаковые (одинаковая длина ленты) — и три до
  первого события, и по числу источников после.
- Переход скелетон ↔ содержимое везде — без анимации, как сейчас.

Есть `noConnectionToServer` «Нет соединения с сервером» — это другая ситуация (сервер не
ответил), новый ключ не дублирует его.

## Вопросы к макетам

1. **«Нет соединения».** Иконка (`WifiSlashIcon` / `CloudSlashIcon` / `PlugsIcon`) и вид на
   уровне страницы и в маленьком блоке (главная «Продолжить чтение», матчинг на тайтле) —
   полный `EmptyState` или компактная строка. Кнопка «Повторить загрузку» есть в обоих.

Анимации поиска, длина мест-скелетонов и наличие кнопки уже решены (см. «Дизайн»).

## Этапы реализации

### Этап 1 — механизм загрузки (только web)

1. `shared/ui/QueryBlock/`: компонент `QueryBlock` — `query`, `skeleton`, `empty` (что при
   ошибке без данных), `children: (data) => ReactNode`; хук тайминга (`hooks/useSkeletonTiming`)
   с задержкой и минимумом; прокрутка к началу блока. Story `UI/QueryBlock`: загрузка, задержка,
   офлайн, ошибка.
2. `shared/ui/OfflineState.tsx` — «Нет соединения» с «Повторить загрузку»; ключи `noConnection`,

## Отвергнутые идеи

- **Затемнение старого контента при смене параметров** (приглушение, размытие, спиннер поверх) —
  смена параметров — новый запрос, поэтому скелетон, как везде.
- **Спиннер там, где ответ часто пустой** (`BlockLoader`) — единообразие важнее, чем редкая
  сетка-скелетон, сменившаяся пустым состоянием. `BlockLoader` удалён.
- **Тихое фоновое обновление** (устаревшее на экране, пока не придёт новое) — противоречит
  принципу «устаревших данных не видно»: человек не понимает, что данные сейчас обновятся.
- **Не перезапрашивать по фокусу вкладки** — устаревшие данные остались бы на экране сколько
  угодно долго.
- **Ничего не показывать при перезапросе после мутации** — у списков нет оптимистичных
  обновлений, и перенесённая или удалённая карточка оставалась бы на месте до ответа.
- **Пометка перезапроса после мутации** (`invalidateWithSkeleton`) — не нужна: скелетон
  показывает любой перезапрос, кроме живых данных.
- **Оптимистичные обновления списков** вместо скелетона — отдельная работа для каждой мутации;
  не в этой задаче.
- **Запрос на каждый источник** (`GET /search/:sourceId`) вместо потока — 12–15 запросов разом,
  по HTTP/1.1 очередь по 6; историю пришлось бы писать отдельно.
- **Секции поиска в порядке прихода** — порядок менялся бы от раза к разу.
- **Матчинг по мере ответов** — результат кэшируется на часы, и обычно ответ мгновенный; блок
  второстепенный; лента сортируется по уверенности, окончательной только после второй волны и
  уточнения — пришлось бы двигать карточки или показывать предварительную уверенность. Остаётся
  одним ответом со скелетоном.
