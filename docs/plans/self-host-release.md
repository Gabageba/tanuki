# Self-host и подготовка к релизу

Статус: **Реализован; внешняя приёмка публикации и HTTPS ожидается** · 2026-11-11
Задача: `self-host-release` · ветка `feat/self-host-release`

Источник: `docs/12-todo.md:116–121`, четыре пункта Фазы 6 из `docs/08-roadmap.md`.
Песочница не нужна: задача не добавляет продуктовый интерфейс.

## Зачем

Владелец небольшого личного или семейного инстанса должен установить Tanuki на Linux-сервер
с доменом и HTTPS, создать первого администратора и прочитать главу по инструкции README.
Для локальной проверки предусмотрен запуск через localhost. Сейчас Compose поднимает только
PostgreSQL, Valkey и Mailpit, а web и API запускаются средствами разработки.

Установка и обновление не требуют Node.js, pnpm или сборки на сервере. Владелец получает
готовые образы и скрипт, сохраняющий конфигурацию и данные. Наблюдаемость помогает отличать
поломки приложения от поломок источников. E2E проверяют путь пользователя через настоящий API
и хранилища, независимо от доступности внешних сайтов.

## Скоуп

- **Входит:** production Dockerfile API и web, полный Compose, Caddy с автоматическим HTTPS,
  подключение через внешний прокси, образы GHCR для `linux/amd64` и `linux/arm64`, скрипт
  установки и обновления, резервирование и восстановление инстанса, автоматические миграции
  отдельным сервисом, явное создание первого администратора, README, запрет индексации,
  опциональный собственный Sentry, закрытые метрики Prometheus, E2E и CI.
- **Потом:** Firefox и WebKit в E2E, расширенные сценарии управления пользователями, аккаунтов
  источников, импорта и пользовательских резервных копий; автоматизация Web Push E2E.
- **Не входит:** публичный сервис с высокой нагрузкой, несколько реплик API, Kubernetes,
  обновления по расписанию, установка Docker и изменение firewall скриптом, почтовый сервер,
  Sentry/Prometheus/Grafana в составе поставки, новый экран мониторинга или мастер настройки
  в браузере. a11y- и перф-аудиты из следующих строк TODO остаются отдельными задачами.

Ручная проверка SSE и push на реальном устройстве из соседнего пункта TODO остаётся отдельной.
Пользовательская резервная копия библиотеки в `apps/api/src/backup/` сохраняет своё назначение;
резервная копия инстанса — административная операция через CLI.

## Сценарии

### Первая установка на сервер

1. Владелец устанавливает Docker Engine и Compose по ссылкам из README, направляет домен
   на сервер и обеспечивает доступ к портам 80/443.
2. Скачивает скрипт выбранного релиза в выбранную папку и запускает `./tanuki install`.
3. Скрипт проверяет окружение, запрашивает домен и параметры внешнего SMTP, создаёт секреты,
   скачивает конфигурацию релиза и образы. Значения паролей вводятся без отображения.
4. Compose дожидается PostgreSQL и Valkey → отдельный `migrate` применяет миграции →
   запускаются API и web. Caddy получает сертификат для настроенного домена.
5. `./tanuki admin-invite` создаёт существующее приглашение администратора и печатает ссылку.
   Оно действует семь дней; при существующем администраторе команда отказывает, как сейчас.
6. Владелец открывает ссылку, регистрируется, подтверждает почту, входит, выбирает источник,
   открывает каталог и главу. Закрытая регистрация и роли не меняются.
7. По желанию запускает `./tanuki push-keys`, указывает `VAPID_SUBJECT` и применяет настройки.
   Отсутствие VAPID-ключей оставляет ленту и SSE доступными, как сейчас.

### Локальная проверка и внешний прокси

1. `./tanuki install --local` создаёт конфигурацию с HTTP на localhost и Mailpit.
   Скрипт печатает адрес приложения и локальный адрес интерфейса Mailpit.
2. Через тот же `admin-invite` владелец регистрируется и подтверждает почту письмом из Mailpit.
3. Для сервера с уже установленным прокси выбирает `--external-proxy`: web слушает HTTP
   на loopback-порту, TLS завершает внешний прокси, `APP_URL` остаётся внешним HTTPS-адресом.
4. README содержит пример подключения и настройки SSE, forwarded-заголовков и доверия прокси.
   Caddy внутри web продолжает раздавать SPA и передавать API на том же origin.

### Обновление и восстановление

1. Владелец явно запускает `./tanuki update <version>`. Без версии команда показывает доступный
   релиз и просит выбрать его; обновления по расписанию нет.
2. Скрипт проверяет совместимость конфигурации и свободное место, скачивает целевой релиз и
   образы до начала простоя. Конфигурация и секреты действующей установки сохраняются.
3. Блокирует параллельные административные операции, прекращает запись через API и фоновые
   задачи, делает согласованную резервную копию БД, конфигурации и серверных токенов.
4. Только после успешного резервирования переключает Compose на целевую версию, запускает
   миграции и API, проверяет готовность и доступность приложения. Простой допустим.
5. При успехе печатает версию, результат проверок и путь к резервной копии.
6. При сбое печатает этап, расположение копии и точную команду восстановления. После начала
   миграций не запускает автоматически старый API поверх потенциально новой схемы.
7. Владелец явно запускает `./tanuki restore <backup>`. Команда объясняет, что данные после
   снимка будут потеряны, требует подтверждения, восстанавливает согласованный набор БД,
   конфигурации, токенов и версии образов, очищает несовместимый кеш и проверяет запуск.

Отмена до переключения версии не меняет действующую установку; если API уже остановлен,
но миграции ещё не начинались, скрипт возвращает исходную версию. После прерывания позднего
этапа сохраняется журнал состояния, позволяющий продолжить восстановление без догадок.

### Подключение мониторинга

1. Владелец задаёт DSN двух проектов своего Sentry: web и API. Без DSN отправка выключена.
2. При ошибке получает очищенное событие с версией релиза и техническим контекстом.
3. Подключает внешний Prometheus к закрытому `/metrics`, используя отдельный токен.
4. По примерам запросов в README смотрит прирост ошибок парсеров по источнику, операции и
   контексту. Sentry, Prometheus и Grafana устанавливает и обслуживает отдельно.

## Логика и правила

### Поставка и Compose

- API и web публикуются в GHCR как согласованная пара образов одного релиза с manifest
  для amd64/arm64. Release bundle содержит точные ссылки на образы с digest и контрольные
  суммы файлов. Изменяемый `latest` не используется для установленной версии.
- Публикация выполняется release-workflow после успешных проверок. README связывает образ
  с версией исходников и лицензией. Сборка из исходников и ручное управление Compose доступны.
- Корневой `docker-compose.yml` становится полным запуском инстанса после заполнения `.env`.
  Нынешняя инфраструктура разработки переезжает в `docker-compose.dev.yml`; команды
  `pnpm docker`, `pnpm start` и раздел разработки README явно используют dev-файл.
- Основные сервисы: `postgres`, `valkey`, одноразовый `migrate`, `api`, `web`.
  `web` — Caddy со статической production-сборкой и проксированием `/api/*` в API.
  Mailpit включается только для локальной проверки и E2E.
- `migrate` ждёт здоровую БД; API ждёт успешное завершение миграций и готовность хранилищ.
  Ошибка миграции завершает операцию с ненулевым кодом и не допускает запуск нового API.
  Каждый переход на новую версию обязан повторно запустить migrator целевой версии;
  нельзя полагаться на оставшийся успешно завершённый контейнер прошлого релиза.
- Изменение схемы при старте самого API не добавляется. Миграции повторяемы по журналу
  Drizzle, параллельное выполнение защищено блокировкой. Один API — ограничение первой версии:
  хаб уведомлений и часть состояния источников сейчас живут в памяти процесса.
- Сборка API включает собранные contracts, parsers, SQL-миграции и исполняемые команды
  миграции/создания инвайта. Скрипт `apps/api/scripts/create-invite.ts` сейчас не входит
  в `src`/`dist`; для production нужен отдельный build CLI, без `tsx` и dev-зависимостей.
- Browser Playwright не устанавливается в runtime API. Браузерный помощник сервисного входа
  LibSocial запускается отдельно там, где есть браузер; полученные файлы можно перенести
  в постоянный каталог токенов. Пользовательская привязка аккаунтов через приложение сохраняется.
- Проверить runtime-версии Node/pnpm по фактическому lockfile и требованиям зависимостей;
  `engines.node >=20` не является достаточным основанием выбирать Node 20 для образа.
  `sharp` и `@node-rs/argon2` должны запускаться на обеих архитектурах.
- Production-контейнер API работает без root; root не требуется и web при согласованном
  выборе внутренних портов. БД и Valkey по умолчанию не публикуют порты наружу.

### Скрипт и конфигурация

- Новый репозиторный скрипт `scripts/self-host/tanuki.sh` попадает в релиз как `tanuki`.
  Команды: `install`, `update`, `backup`, `restore`, `admin-invite`, `push-keys`, `status`.
- Повторный `install` не перезаписывает существующие секреты, конфигурацию и volumes;
  сообщает о найденной установке. `update` добавляет новые параметры с безопасными
  значениями либо просит заполнить обязательные, сохраняя пользовательские настройки.
- До первого запуска проверяются Docker/Compose и поддерживаемая архитектура, обязательные
  поля, занятость нужных портов, DNS для домена, получение образов и подключение/авторизация
  SMTP без отправки тестового письма. Невозможность проверки не считается успехом.
- Скрипт объясняет необходимость внешней доступности 80/443, которую локальная проверка
  портов не доказывает. Проблема выдачи сертификата отображается как отдельный этап запуска.
- Скрипт не устанавливает Docker и не изменяет firewall. Ошибка содержит причину и действие
  для исправления, секреты в вывод не попадают. Пароли не подставляются через `eval` или
  небезопасное shell-выполнение; специальные символы проверяются при записи `.env` и URL БД.
- Генерируются случайные пароль БД, `IMG_SIGN_SECRET`, `SOURCE_SECRETS_KEY`, `METRICS_TOKEN`.
  Создание VAPID-ключей — отдельная явная команда, не заменяющая существующую пару.
- SMTP обязателен для серверного сценария с подтверждением email. Log-fallback
  `MailService` остаётся средством разработки; успешную серверную установку через него
  не объявляем. Локальная проверка использует Mailpit без изменения регистрации.
- Конфигурация сервера включает внешний `APP_URL`, режим прокси, SMTP, ключи, версию релиза,
  опциональные VAPID и Sentry. `COOKIE_SECURE` включён для внешнего HTTPS и выключен локально.
- Доверие forwarded-заголовкам ограничено известным прокси/сетью. Текущий `TRUST_PROXY=true`
  доверяет всем отправителям; при реализации уточнить конфигурацию Fastify так, чтобы внешний
  клиент не подменял IP для rate limit. При внешнем прокси описать обе границы доверия.

### Данные и резервирование

| Что                                                                        | Где хранится                                             | Резервирование                                |
| -------------------------------------------------------------------------- | -------------------------------------------------------- | --------------------------------------------- |
| Аккаунты, библиотека, прогресс, аватары, уведомления и привязки источников | PostgreSQL volume                                        | Полный согласованный dump                     |
| Секреты, SMTP, настройки, версия и digest образов                          | Папка установки, закрытые файлы                          | Вместе с dump и манифестом копии              |
| Сервисные токены LibSocial                                                 | Постоянный каталог, заданный `LIBSOCIAL_TOKEN_STORE_DIR` | Вместе с БД и конфигурацией                   |
| Сертификаты Caddy и ACME-состояние                                         | Постоянный volume Caddy                                  | Включить в копию; это не кеш контента         |
| Кеш API и изображений в Valkey                                             | Volume Valkey                                            | Восстанавливается запросами, не нужен в копии |
| Скачанные главы, очередь, несинхронизированный прогресс                    | Браузер: IndexedDB/Cache Storage                         | Не входят в серверную копию                   |

Скрипт не сохраняет страницы манги на диске сервера. Закрытые файлы и архивы доступны только
владельцу установки; резервные копии содержат действующие секреты и должны переноситься как
секреты. Формат копии версионирован, содержит дату UTC, версию приложения, состав и контрольные
суммы. Проверка архива и доступности нужных образов выполняется до изменения текущих данных.

Автоматическое удаление старых копий и облачная выгрузка не входят. Перед резервированием
проверяется место, неполный архив не считается пригодной копией. Не использовать
`docker compose down -v` в установке, обновлении или восстановлении.

### Прокси, SPA и PWA

- Web и API имеют общий origin; production не зависит от dev-прокси Vite и не требует
  отдельного публичного API-домена или CORS.
- `/api/*` проходит в API с исходным путём, методами, cookie и статусами. SPA fallback
  применяется только к навигации, не превращает ошибку API или отсутствующий asset в HTML.
- SSE поиска и уведомлений передаётся без накопления ответа до закрытия, с heartbeat и
  достаточными таймаутами. Проксирование изображений остаётся потоковым.
- Прокси не уменьшает существующие лимиты аватаров и резервной копии библиотеки.
  Подтверждение почты и сброс пароля используют правильный внешний `APP_URL`.
- `index.html`, `/sw.js` и публичная runtime-конфигурация обновляются без долгого HTTP-кеша;
  hashed assets имеют длительный immutable-кеш. Учесть обновление старой открытой вкладки
  и отсутствие её lazy chunks после переключения версии: проверить восстановление через
  существующий механизм обновления/обработки ошибки загрузки, не создавать цикл reload.
- Смена серверного релиза не вызывает принудительный `skipWaiting`: действующее предложение
  обновления PWA и завершение скачиваемой главы сохраняются по `docs/06-pwa-offline.md`.
- `GET /api/v1/health` остаётся liveness. Добавляется `GET /api/v1/health/ready` с ограниченными
  по времени проверками PostgreSQL и Valkey; он не обращается к сайтам-источникам.
  Неготовность зависимости даёт 503 для проверки готовности, не отменяя существующий
  fallback приложения при отказе кеша. Проверка не раскрывает адреса, пароли и исключения.

### Запрет индексации

- Добавить `apps/web/public/robots.txt`: `User-agent: *` и `Disallow: /`.
- В `apps/web/index.html` добавить `<meta name="robots" content="noindex">`.
  SPA отдаёт его и для вложенных маршрутов; правило действует и для auth-страниц.
- В конфигурации Caddy добавить `X-Robots-Tag: noindex` для ответов web/API; пример внешнего
  прокси сохраняет это правило. Метрики не становятся публичными ради заголовка.
- Не обещать удаление уже известных URL из поисковой выдачи: при `Disallow: /` робот может
  не прочитать `noindex`. Это принятая комбинация из TODO, а доступ к данным по-прежнему
  контролируется авторизацией. Переключатель включения индексации не добавляется.

### Sentry

- Использовать SDK для React и NestJS; инициализация API должна происходить до загрузки
  инструментируемых модулей. Существующий `HttpExceptionFilter` и фоновые `catch` требуют
  явного подключения: один глобальный SDK-hook не увидит все перехваченные ошибки.
- Отправлять неожиданные исключения web/API, ошибки фоновых задач и `PARSER_FAILED`.
  Ожидаемые отказы входа, валидация, rate limit, offline и обычная недоступность источника
  не становятся отдельными событиями Sentry только из-за HTTP-статуса.
- На API ошибка парсера отправляется там, где классифицирован реальный вызов, до fallback.
  Ошибка не отправляется повторно из `HttpExceptionFilter` или браузера. Для остальных
  серверных сбоев аналогично назначить одно место отправки; браузер сообщает собственные
  исключения, а не копирует каждую ошибку API.
- `sendDefaultPii: false`; replay, tracing, profiling и автоматическая отправка логов
  выключены. Не добавлять идентификаторы пользователей, почту, историю чтения, тела запросов,
  cookie, authorization, пароли, токены, инвайты, параметры поисковых запросов и signed URL.
- Очистка применяется ко всем частям события, включая breadcrumbs, URL, exception message,
  extras и stack context. Для `PARSER_FAILED` передавать нормализованное техническое описание,
  sourceId, операцию и контекст вместо произвольного HTML или текста ответа источника.
- Разрешённый диагностический минимум: release, environment, слой web/API, нормализованный
  маршрут, код ошибки и ограниченные технические метки. Группировка не зависит от titleId,
  chapterId или полного URL. Массовый сбой группируется в Sentry; метрика считает все вызовы.
- Образы универсальны для инстансов: DSN web задаётся при запуске контейнера через
  генерируемый `/runtime-config.js`, загружаемый перед приложением. Файл содержит только
  публичную конфигурацию, имеет `no-store` и исключён из SW precache/runtime cache.
  В dev допускается пустая конфигурация. API получает DSN из env.
- Разбор стеков: release bundle содержит sourcemaps отдельно от публичной статики и
  инструкцию загрузки в свой Sentry. Токен загрузки не попадает в web, образы или архив
  общедоступного релиза. Отсутствие Sentry или ошибка доставки не мешают работе приложения.

### Метрика ошибок парсеров

Имя: `tanuki_parser_failures_total{source_id,operation,context}` — Prometheus counter.
Процессные счётчики сбрасываются при перезапуске API, историю хранит внешний Prometheus.

- Единица — один завершившийся ошибкой вызов метода парсера, классифицированный через
  `toApiException` как `API_ERROR_CODE.PARSER_FAILED`. Внутренние HTTP-retry одного вызова
  не считаются отдельными вызовами; новый вызов после клиентского retry считается отдельно.
- Учитываются пользовательские запросы, фоновые обновления/совпадения, пробник и ошибки,
  скрытые fallback из кеша. HTTP-filter не является местом подсчёта.
- Cache hit, отказ breaker/очереди до вызова парсера, 404, авторизация и сетевой отказ с другим
  кодом метрику не увеличивают. Не увеличивать счётчик повторно при нескольких обработчиках.
- `source_id` — существующий ID источника. `operation` — имя вызываемого метода из
  конечного перечня интерфейса `Parser`, например `getList`, `getDetails`, `getPages`.
  Не помещать URL, пользователя, текст ошибки и динамические идентификаторы в labels.
- Для `context` добавить серверный const-объект и тип через `EnumLiteralsOf`:

  ```ts
  export const PARSER_CALL_CONTEXT = {
    REQUEST: 'request',
    BACKGROUND: 'background',
    PROBE: 'probe',
  } as const;
  ```

  Операции также объявить один раз const-объектом с UPPERCASE-ключами, производным типом
  и значениями, совпадающими с методами парсера. Enum относится к серверной телеметрии;
  в `packages/contracts` его не выносить без потребителя в web.

- Ввести единый слой наблюдения за вызовом на серверной границе парсеров и явно передавать
  контекст от инициатора. Учесть `ParsersClientService.probe`, который сейчас возвращает
  строку ошибки и обходит `guardedFetch`, и прямые вызовы парсеров вне этого сервиса.
  Для многошагового пробника учитывать упавший метод, не весь прогон плюс метод дважды.
- `/metrics` обслуживается на отдельном внутреннем порту API (предлагаемый `9464`), а не
  через сессионный AuthGuard. Доступ требует bearer `METRICS_TOKEN`; без токена endpoint
  выключен. Web-прокси этот порт не публикует, публичный `/metrics` возвращает 404.
- Prometheus подключается через согласованную Docker-сеть или явно настроенный частный
  маршрут/loopback-порт; README не предлагает открыть метрики в интернет.
  Отсутствие Prometheus не влияет на приложение.
- README содержит scrape-конфигурацию и запросы `sum by (source_id) (increase(
tanuki_parser_failures_total[1h]))` и `sum by (source_id, operation, context) (rate(
tanuki_parser_failures_total[5m]))`.

## E2E и проверки

- Тестовый стек: production web/Caddy, настоящий API, PostgreSQL, Valkey, Mailpit и локальный
  HTTP-сервер источников с фиксированными каталогом, деталями, главами, картинками и ошибками.
  Ответы `/api/v1/*` в браузере не подменяются через MSW.
- Добавить изолированный тестовый bootstrap API с реальными модулями приложения и адаптером
  источников, направленным на fixture-server. Парсинг HTML/JSON и image proxy действительно
  выполняются; использовать фикстуры поддерживаемого движка, а не готовые ответы API.
  Production entrypoint не умеет включать тестовые маршруты, seed или произвольную замену
  источников. Не ослаблять `img-proxy/upstream-guard.ts` для production ради localhost.
- Тестовая инъекция реестра/HTTP-транспорта — локальная точка расширения, не замена BFF.
  Разрешить fixture-host только в тестовом bootstrap. Внешние исходящие запросы запрещены;
  реальные источники продолжают отдельно проверяться ночными контрактными тестами.
- Отдельный smoke запускает именно production entrypoint без тестовой подмены и проверяет
  миграции, readiness, web и авторизацию без обращения к сайтам-источникам.
- Тесты имеют изолированный Compose project и БД, не используют рабочие `.env` и volumes.
  Регистрация читает письмо через Mailpit API и проходит настоящее подтверждение токена.

Обязательные сценарии:

1. Чистая установка → миграции → готовность → создание первого admin-инвайта → регистрация
   и подтверждение email → вход. Повторный bootstrap не создаёт второго администратора.
2. Каталог → поиск, включая потоковый ответ → тайтл → глава. Изображения проходят image proxy.
3. Закладка и прогресс сохраняются после reload, нового входа и перезапуска API.
4. Скачивание главы → отключение сети → повторное открытие приложения и главы → локальное
   чтение и очередь прогресса → возврат сети и синхронизация.
5. SSE через Caddy: доставка события и heartbeat, восстановление после штатного перезапуска,
   сохранение правила остановки вытесненного потока из `notifications-stream-limit`.
6. Повреждённый ответ фикстуры → один прирост метрики и одно очищенное событие Sentry;
   отдельно проверить fallback, background и probe, отсутствие ложного счёта cache hit.
   Доставка Sentry проверяется локальным приёмником событий, без настоящего Sentry.
7. Закрытость метрик: без bearer доступа нет, с токеном внутри сети есть, с публичного
   web-порта нет. Отсутствие DSN не вызывает исходящих Sentry-запросов.
8. `robots.txt`, meta и HTTP-заголовок на корне и вложенном маршруте; SPA fallback не
   применяется к API, assets и метрикам. Публичная конфигурация не содержит секретов.
9. Smoke обновления: исходный релиз/снимок → данные пользователя → backup → обновление →
   данные сохранены; ошибка миграции/готовности → явное восстановление → согласованная старая
   версия и данные. Для первого релиза до появления предыдущего опубликованного образа
   использовать воспроизводимый тестовый baseline БД и тестовую версию образа.
10. Повторный install, занятый порт, недоступный SMTP/registry, повреждённая копия и нехватка
    места завершаются понятной ошибкой без потери конфигурации и данных.

На каждом PR и push в `master` запускается полный согласованный набор: Chromium desktop и
Chromium mobile. Mobile — эмуляция viewport/touch, не замена проверки реального Android/iOS.
Обе темы и переводы уже покрываются Storybook; основная функциональная E2E-матрица не
умножается на них без отдельной причины. Установка, миграции, update/restore и CLI имеют
отдельные интеграционные проверки и не дублируются на каждый viewport.

При ошибке CI сохраняет Playwright trace, HTML-отчёт и диагностические логи тестового стека.
В них используются только фиктивные пользователи и секреты; срок хранения — 14 дней,
как у текущего visual-report. Версия Playwright и browser image согласована с lockfile.
Новые проверки дополняют визуальные тесты Storybook и существующие unit/browser-тесты.

## Этапы реализации

1. **Основа поставки.** Зафиксировать конфигурацию и границы сервисов, runtime-версии,
   production CLI миграций и admin-инвайта, форматы release bundle и backup. В контракт API
   добавить только readiness; новые доменные enum и поля не требуются.
2. **Контейнеры и прокси.** Dockerfile обоих приложений, Caddy, full/dev Compose, volumes,
   healthchecks, миграции до API, localhost/Mailpit, внешний прокси, noindex. Проверить
   потоковый SSE, cookie, IP/rate limit, SPA и лимиты запросов на реальном транспорте.
3. **Установка и эксплуатация.** Скрипт, конфигурация, генерация и сохранение секретов,
   резервирование, update/restore, блокировки и диагностика отказов. Проверки согласованности
   копии, повторного запуска и ошибок миграции обязательны.
4. **Наблюдаемость.** Единый учёт вызовов парсеров и контекста, закрытый `/metrics`, Sentry
   web/API/background, runtime DSN web, очистка событий, sourcemaps. Проверки метрики и
   удаления чувствительных данных — до подключения к настоящему Sentry.
5. **E2E.** Fixture-server и тестовый bootstrap с реальными слоями приложения, полный набор
   Chromium desktop/mobile, smoke production и update/restore. Включить на PR и master.
6. **Публикация.** GHCR multiarch, release bundle со скриптом, конфигурацией, digest и
   контрольными суммами. Проверить запуск обеих архитектур; один успешный cross-build
   не заменяет проверку запуска native-модулей. Обновление документации и проверка README
   на чистой машине завершают этап, затем `/commit`.

Все этапы выполняются без макетов. План не разрешает прямо сейчас публиковать релиз или
образы: эта стадия задаёт будущий процесс поставки; текущий результат — только документ.

## Критерии приёмки

- Незнакомый с репозиторием человек поднимает Linux-инстанс с HTTPS по README без Node.js,
  подтверждает почту первого администратора и читает главу. Ручной Compose тоже документирован.
- Localhost с Mailpit и схема с внешним прокси проверены; dev-команды продолжают поднимать
  только инфраструктуру разработки.
- Образы API/web доступны для двух архитектур, связаны с одной версией и исходниками.
- Миграции завершаются до нового API; повторная установка и обновление сохраняют данные,
  секреты, привязки источников и VAPID. Backup/restore проверены с искусственным отказом.
- `robots.txt`, meta и заголовок присутствуют, API и статические файлы не попадают под
  ошибочный SPA fallback.
- Sentry опционален; события очищены и не дублируются. Счётчик считает каждый подходящий
  вызов, включая fallback/background/probe; `/metrics` закрыт от публичного доступа.
- Все согласованные E2E проходят на PR и master; реальные сайты не являются зависимостью.
- Пройдены проверки проекта, затронутых пакетов и документации по правилам последующего
  ревью. Новые интеграционные проверки покрывают риски данных, а не повторяют реализацию.

## Реализация и проверка — 2026-11-11

- Production/dev Compose разделены. API: Node 24.20.0, unprivileged runtime, production CLI,
  Drizzle migrator с advisory lock; Caddy: непривилегированные 8080/8443, отдельный локальный
  healthcheck, SSE, точное доверие прокси, noindex. Формат конфигурации и backup — версия 1.
- Минимум скрипта: Docker Engine 24.0 и Compose 2.30 (raw env_file); фактически проверены
  Docker 29.4.2 / Compose 5.1.3. `undici@8.9.0` требует Node >=22.19, выбран Node 24.
- SMTP и произвольные однострочные секреты читаются из `api.env` без интерполяции; параметры
  Compose и генерируемые секреты — `.env`. Архив включает скрытый `.env` в SHA256-манифест.
  Незавершённая операция блокирует новые изменения до разбора журнала/восстановления.
  `recover` продолжает прерванную первую установку с сохранённой конфигурацией; после сбоя
  backup до миграций журнал снимается только при восстановленной готовности приложения.
  Обновление с начавшимися миграциями требует явного `restore`.
- Проверен production entrypoint: fresh migrations, readiness, авторизация, admin-invite,
  регистрация/почта, пользовательские настройки → backup → тестовая версия → отказ миграции →
  явный restore согласованных версии/данных/конфигурации. CLI-тесты: повторный install,
  блокировка, registry/диск до простоя, повреждённый архив, запрет автоматического старого API.
- Chromium desktop/mobile: настоящий AComics HTML-парсер с HTTP fixture-server, реальные API,
  БД/Valkey/Mailpit/Caddy; каталог/поиск/глава/image proxy, bookmark/progress, рестарт и SSE,
  heartbeat/stop, скачивание, offline reload, очередь прогресса и её синхронизация, новый вход.
  Browser runner делит сетевой namespace Caddy, поэтому origin остаётся localhost; сеть
  `internal: true` запрещает внешний egress. Тестовые overrides/control-сервер собираются
  только в target `e2e`, production их не содержит.
- Наблюдение охватывает методы чтения и decodeImage. Проверены request/background/probe,
  stale fallback, отсутствие счёта cache hit, bearer и публичный 404 метрик, три очищенных
  события через локальный Sentry envelope receiver. Исправлен heartbeat: Nest отбрасывает
  пустой `data`, поэтому ping теперь содержит `{}`. SDK без DSN не инициализируется.
- ARM64 production smoke и native sharp/argon2 прошли; amd64 образ собран и эти native-модули
  запущены под эмуляцией. Release workflow дополнительно требует native runners обеих
  архитектур и анонимный GHCR pull. Размеры локальных arm64-образов (`docker image inspect`):
  API 115 402 063 байт, web 26 926 252 байт; это не гарантия расхода RAM/CPU или места под БД.
- Старая вкладка со SW использует precached chunks прежней сборки; без SW недоступный lazy
  chunk остаётся на существующем экране ошибки с явной перезагрузкой, без reload-цикла.
  Принятие обновления и завершение скачиваемой главы не изменены.
- GHCR-пакеты workflow: `ghcr.io/gabageba/tanuki-api` и `ghcr.io/gabageba/tanuki-web`.
  Образы/релиз в этой реализации не публиковались; первый тег выбирает владелец. Требуется
  включить публичность пакетов. Draft bundle содержит digest, CLI, примеры env, README,
  лицензию, контрольные суммы и отдельные sourcemaps. Живой ACME/HTTPS на домене и анонимный
  pull опубликованных образов остаются внешней приёмкой; без домена/публикации они не объявлены
  пройденными. Минимальный сервер по RAM/CPU требует отдельного замера на целевой машине.

## Отвергнутые идеи

- Только сборка на сервере — основной путь должен быть проще: скрипт и готовые образы.
- Только ручные миграции — выбран отдельный migrator в одном Compose-запуске.
- Автообновление по расписанию и слепой откат образов — выбран явный update и восстановление
  согласованной копии после потенциально несовместимой миграции.
- Мастер первого запуска в браузере и регистрация без email — используем CLI-инвайт и SMTP.
- Полный стек Sentry/Prometheus/Grafana внутри Tanuki и новая панель — подключаем внешние
  инструменты владельца, не увеличиваем обязательную поставку.
- Подсчёт только HTTP-ошибок пользователя — пропустил бы фон, probe и скрытый fallback.
- E2E только на MSW или настоящих сайтах — не проверяет BFF либо зависит от внешних сбоев.
- Расширенная E2E-матрица и полноценный публичный хостинг — отдельные последующие задачи.
