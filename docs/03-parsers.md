# 03 — Слой парсеров

## Итог: свой TS-пакет, а не JVM-сайдкар поверх kotatsu

До июля 2026 парсинг источников жил в `apps/parsers` — Ktor-сервис на JVM, линковавший форк
`kotatsu-parsers-redo` (~1000 источников на десятках языков) и отдававший BFF (`apps/api`)
сериализованные доменные объекты по HTTP.

Причина отказа от этой схемы простая: из тысячи источников библиотеки нужны только русские —
23 штуки. «Кто-то другой чинит парсер, когда сайт меняет вёрстку» — вот единственный
содержательный довод в пользу внешней библиотеки — на практике не работал даже для этих 23:
все патчи, когда-либо влившиеся в форк (`LibSocialParser`/MangaLib, `DesuMeParser`, RU-фиксы
`GroupleParser`), были написаны нами же, а не пришли из апстрима. Оставалась только цена: второй
рантайм (Gradle, JVM toolchain, JitPack, отдельный Dockerfile, два CI-джоба) ради 977 источников,
которыми никто не пользуется.

**Текущая архитектура: `packages/parsers` — TS-библиотека, импортируемая в процесс `apps/api`.**
Никакого HTTP-хопа, никакого второго рантайма. `apps/api/src/parsers-client/parsers-client.service.ts`
держит реестр парсеров (`ParsersRegistry` из `@tanuki/parsers`) и вызывает его методы напрямую;
кеш, circuit breaker и rate-limiter (см. «Устойчивость» ниже) работают точно так же, как раньше,
просто оборачивают прямой вызов вместо HTTP GET.

Логика самих 23 парсеров — **порт** соответствующего кода из
[`Kotatsu-Redo/kotatsu-parsers-redo`](https://github.com/Kotatsu-Redo/kotatsu-parsers-redo)
(и нашего форка `Gabageba/tanuki-parsers-redo` поверх него) на TypeScript, а не переписывание с
нуля по вёрстке сайтов — там годами накоплено знание вида «Desu переехал на XenForo и `/manga/
api/` отдаёт 410», «SelfManga 301-редиректит на `1.selfmanga.live`», которое дороже всего
переоткрывать заново. Поскольку это перевод GPLv3-кода на другой язык, весь репозиторий теперь
распространяется под GPLv3 — детали в [09 — Правовые аспекты](09-legal.md).

## Архитектура `packages/parsers`

```

  src/
    index.ts              # единственная точка экспорта
    types.ts              # RawTitle/RawChapter/RawPage/RawTag/RawSourceInfo
    errors.ts              # иерархия ParserError (framework-free)
    registry.ts            # SOURCE_IDS, SOURCES, createRegistry()
    core/
      parser.ts            # интерфейс Parser, ParserContext, ListParams
      paging.ts             # planWindow / fetchPaged / fetchOffsetNative
      uid.ts                 # generateUid (FNV-1a, стабилен между рестартами)
      http/                  # свой HttpClient поверх undici: редиректы + куки + декомпрессия
      html/                  # cheerio-обёртка (dom, selectors, urls)
      text/                  # RU-даты, строки, числа
    sources/
      grouple/              # 1 движок → READMANGA_RU, MINTMANGA, SELFMANGA, SEIMANGA, USAGI, ALLHENTAI
      desu/                  # DESUME
      ...                    # остальные 16 движков по мере портирования
  test/                     # фикстурные тесты + conformance-набор (каждый PR)
  contract/                 # живые контрактные тесты (только ночной CI)
```

### Интерфейс `Parser`

```ts
export interface Parser {
  readonly id: string;
  readonly info: RawSourceInfo; // статика, без сети
  getList(params: ListParams): Promise<RawTitle[]>; // chapters ОБЯЗАН быть null
  getDetails(url: string): Promise<RawTitle>; // chapters заполнены
  getPages(chapterUrl: string): Promise<RawPage[]>; // url абсолютный, преразрешённый
  getHome?(): Promise<RawHomeSection[]>; // блоки главной сайта — для подборок
  getBookmarks?(): Promise<RawBookmarkFolder[]>; // закладки аккаунта — для импорта из источника
  imageHeaders(imageUrl: string): Record<string, string>;
  init?(): Promise<void>; // разовый прогрев (SSO Grouple)
  close?(): Promise<void>;
}
```

`getBookmarks` читает закладки от аккаунта пользователя (`currentSourceAccount`) по папкам сайта:
`RawBookmarkFolder { id, builtIn, name, items }`, стандартный статус сайта → встроенная папка
(`builtIn`), своя папка сайта — `builtIn: null`; `RawBookmark` — `id` и `url` как у `getList`,
снимок тайтла, `lastChapterNumber` и `lastChapterVolume` («где остановился», `null`, если сайт не
отдаёт; том нужен там, где нумерация глав начинается заново в каждом томе — так у LibSocial).
`RawSourceInfo.isBookmarksImportSupported` реестр выводит из наличия метода — в движке флаг не
пишется. Реализован в LibSocial (MangaLib, HentaiLib — у SlashLib входа нет, метода тоже), Desu,
MangaBuff, всех источниках движка Grouple (ReadManga, MintManga, SelfManga, SeiManga, Usagi,
AllHentai), ReManga, TomiloLib, WaManga, HentaiChan, Senkuro, Senkognito и сети inuko (Inkstory, PureManga);
Nude-Moon ждёт образцов ответов сайта
([plans/source-import.md](plans/source-import.md)).

LibSocial (проверено вживую 2026-10-26): id аккаунта — `GET /api/auth/me`, папки —
`GET /api/bookmarks/folder/{userId}` (общие на всю сеть, у каждой `site_ids` и `count`; 1–4 —
«Читаю», «В планах», «Брошено», «Прочитано», 5 — «Любимые», дальше свои папки, 21+ — аниме-сайт),
закладки папки — `GET /api/bookmarks?user_id=&status=<id папки>&page=` по 24 до пустого
`links.next` (проверено на 30 закладках: 24 + 6). Закладки других сайтов сети отсеиваются по
`media.site`, «где остановился» — `item.volume` и `item.number` (`item.model: 'chapter'`). Свои
папки человека создаются с `site_ids` одного сайта.

Desu (проверено вживую 2026-10-26): id аккаунта — `visitor: { user_id }` в конфиге XenForo любой
страницы (у гостя 0), список — `GET /manga/list/{userId}/` (редирект на `/manga/list/<slug>.<id>/`),
одна страница без пагинации: по таблице `#status_<статус>_block` на статус, свёрнутые тоже в
разметке. Статусы — `data-status` формы «Добавить в список»: `watching`, `planned`, `completed`,
`dropped`, `favorites` («Любимое») — встроенные папки, `on_hold` («Отложено») → встроенная «Отложено»; других
папок у сайта нет. «Где остановился» — ссылка колонки «Закладка» (`/vol4/ch24/`, том и глава), без
неё — счётчик «Главы» (сколько прочитано, без тома). Обложки списка — `x120`, берём `preview`.

MangaBuff (проверено вживую 2026-10-29): id аккаунта — `window.user_id` в конфиге любой страницы
(у гостя 0). Список — `GET /users/{userId}/bookmarks`, открыт и гостю, но свои папки бывают
скрытыми, поэтому читается от аккаунта. Папки — боковое меню (`.side-menu__item[data-folder-id]`
со счётчиком; «Весь список» без id — сумма остальных): 1–4 общие на всех — «Читаю», «Буду
читать», «Прочитано», «Заброшено» → встроенные, свои папки — с id от тысяч. Закладки папки —
`?folder_id=&page=` по 150, следующая страница есть, пока на неё ссылается `.pagination`; пустую
по счётчику не открываем. «Где остановился» — ссылка «Прочитано до N» (`/manga/<slug>/<том>/
<глава>`); «1 том, 23 глава» в строке — последняя глава тайтла, не позиция. Обложки — `x70`,
берём `x180`. «Избранное» рядом — лайки сайта (манга, главы, карточки, колоды), не папка чтения,
не импортируется.

Сеть inuko — Inkstory и PureManga (проверено вживую 2026-10-27): сессия сайта нужна только узнать,
чей аккаунт, — id вошедшего в SSR-состоянии `/faq` (`currentUser`). Страница открывается на домене,
где лежит cookie в jar аккаунта (`findInukoSessionDomain`): id пользователя в сети общий, поэтому
cookie, перенесённая с PureManga, открывает и библиотеку Inkstory. Дальше общий API `api.inuko.me` отдаёт
библиотеку по `userId` без авторизации: папки — `GET /v2/folders?userId=` (пять системных —
«Читаю», «В планах», «Брошено», «Прочитано», «Любимые» → встроенные, созданные человеком —
свои; ключа статуса у папок нет, только имя), книги в них — `GET /v2/folder-items?userId=` (только
`bookId`; `serviceName` сайта отсеивает книги соседних сайтов сети, которые сайт показывает в
библиотеке при «показывать все сервисы»), сами книги — `GET /v2/books?id=…&id=…` пачками по 100.
Книги «только в библиотеке» (`readingRestriction: LIBRARY_ONLY`) список не отдаёт — их берём
по одной из `/v2/books/{id}`. «Где остановился» — `GET /v2/bookmarks?userId=` (место чтения,
запись на каждую открытую ветку перевода — берём самую свежую), номер и том — из
`/v2/chapters/{chapterId}`, запрос на тайтл. Списки листаются до пустой страницы: потолок `size`
у эндпоинтов разный (у `/v2/books` — 100), у `/v2/bookmarks` по умолчанию 20.

MintManga (проверено вживую 2026-10-29 на пустой библиотеке): кабинет на SSO-шлюзе
`3.grouple.co`, `GET /private/bookmarks` отдаёт `BOOKMARK_SETTINGS` с названиями и доступностью
трёх пользовательских папок. Список — штатный запрос чтения `POST /api/bookmark/list`,
`Authorization: Bearer <gwt>` из сессии пользователя. В теле `siteFilter: [2]`,
`statusFilter: [статус]`, `includeUpdates: true`, `limit: 50`, `offset`; ответ — `list` и `total`.
`WATCHING`, `PLANED` (написание API), `COMPLETED`, `DROPPED`, `FAVORITE` → встроенные папки;
`ON_HOLD` («Отложено») → встроенная «Отложено»; `REVIEWING` и включённые `USER_DEFINED*` → свои.
Удалённое не запрашивается.
Тайтл — `element.elementUrl`, `name`, `picUrl`; чужие сайты и отзывы отсеиваются.
Позиция — `resume.url` вида `/slug/vol3/12.5`, без ссылки прогресс неизвестен.
Остальные источники движка используют тот же парсер: ReadManga и Usagi — `siteFilter: [1]`,
SelfManga — `[3]`, SeiManga — `[21]`; AllHentai — `[1]` через отдельный шлюз `z.qawa.org`
и собственную семью авторизации. Фильтрация сайтов, папки, пагинация, позиция чтения и выбор
шлюза и аккаунта проверены фикстурными тестами для всех шести источников.
Формат заполненных строк подтверждён JavaScript-клиентом сайта и фикстурными тестами;
живая сервисная учётная запись закладок MintManga не содержит. Возможность импорта включена
у всех источников общего движка; живая проверка импорта остальных сайтов ещё не проводилась.

ReManga (API и параметры сверены с публичным JavaScript-клиентом 2026-10-30; импорт
заполненного личного аккаунта пока не проверен вживую): основной вход —
`POST /api/users/login/` с `user` (логин или почта) и `password`, токен — `content.access_token`.
Неверные данные возвращают 400 (проверено на заведомо несуществующем тестовом адресе),
`content.two_factor_auth` требует входа в браузере. Запасной способ для соцсетей и 2FA —
перенос cookie `auth:token`. При 401 и сохранённом пароле сервер один раз входит заново;
параллельные запросы одного jar используют общий повторный вход. Без сохранённого пароля
человек входит заново сам. Сессия — cookie `auth:token` сайта,
запросы API получают её значение как `Authorization: Bearer …`. Аккаунт —
`GET /api/v2/users/current/`, папки — `/api/v2/users/{id}/user_bookmarks/`, закладки —
`/api/v2/users/{id}/bookmarks/?type=<id папки>&page=`. Списки — `results`, страницы до пустого
`next`; адрес из `next` не используется. Встроенная папка определяется по `type`, а не `id`:
1 — «Читаю», 2 — «Буду читать», 3 — «Прочитано», 4 — «Брошено», 5 — «Отложено», 7 — «Любимые»;
6 («Не интересно»), 8 (пользовательская) и неизвестные типы остаются своими папками. Снимок
тайтла — `title`, `id` и `url` нормализуются тем же кодом, что у каталога. `read_progress` —
счётчик прочитанных глав, поэтому номер и том последней главы остаются `null`.

TomiloLib (публичный JavaScript-клиент и ответы на неверные тестовые данные проверены
2026-10-30; полный импорт личной библиотеки пока не проверен вживую): вход —
`POST /api/auth/login` с `email` и `password`, ответ — `data.access_token` и
`data.refresh_token` (также принимается ответ без обёртки `data`). Неверные данные — HTTP 401.
Токены хранятся в зашифрованном jar аккаунта; запросы получают `Authorization: Bearer …`.
При 401 — один `POST /api/auth/refresh` с `refresh_token`, затем повтор запроса. Если refresh
отвергнут и пароль сохранён — повторный вход; иначе аккаунт требует войти заново.
Одновременные запросы одного jar используют одно обновление, новые токены сохраняются.
Закладки — полный список `data.bookmarks` из `GET /api/users/profile`, пользовательские
группы — `GET /api/users/profile/bookmark-groups` (`id` вида `group:<id>`, `name`).
`reading`, `planned`, `completed`, `favorites`, `dropped` → соответствующие встроенные папки;
группы остаются своими папками. Снимок берётся из заполненного `titleId` или `title`, старые
закладки с одним id догружаются через `/api/titles/<id>?populateChapters=false`.
Удалённые тайтлы пропускаются. Номера глав — из полной истории
`/api/users/profile/history?page=&limit=100&light=false`, все страницы `pagination.pages`;
максимальный прочитанный номер, включая 0 и дробные, том — `null`. Счётчик прочитанных глав
не используется как номер. Повреждённый ответ или ошибка страницы прерывает импорт.

WaManga (OpenAPI и публичный JavaScript-клиент сверены 2026-10-31; полный импорт личного
аккаунта пока не проверен вживую): вход — `POST /api/v1/auth/login` с `username` и `password`,
ответ — `access_token` и `refresh_token`. Токены сохраняются в зашифрованном jar аккаунта.
Запросы получают `Authorization: Bearer …`; при 401/403 — один `/api/v1/auth/refresh`
с `{ token: refresh_token }` и прежним Bearer. Если обновление отвергнуто, сохранённый пароль
позволяет войти заново. Одновременные запросы делят обновление; новая пара сохраняется.
Библиотека — `GET /api/v1/user/library?limit=50&offset=`, массив до страницы короче 50.
`reading`, `completed`, `planned`, `on_hold`, `dropped` → встроенные папки.
`favorite` — отдельный признак: тайтл виден и в статусе, и в «Избранном»; при выборе всех
папок импорт берёт его в «Любимое» по общему правилу первой папки. Записи только из истории
(`status: null`, `favorite: false`) не становятся закладками. `mangaId`, `type`, `slug`,
`title`, `coverUrl` дают снимок с теми же id и url, что каталог; возрастной рейтинг неизвестен.
`chapterPosition` — номер главы, включая 0 и дробные; том — `null`. Ошибка страницы,
неизвестный статус, повреждённый ответ или повтор полной страницы прерывают импорт.

Senkuro и Senkognito (публичный клиент и гостевые ответы GraphQL сверены 2026-10-30;
полный импорт личной библиотеки пока не проверен вживую): перенос одной cookie `access_token`
с любого сайта для общей привязки семейства `senkuro`,
поскольку вход по почте и паролю через SSO требует капчу: `sso.senkuro.org` предпочитает
Cloudflare Turnstile, `sso.senkuro.net` — Yandex SmartCaptcha (`/api/v1/captcha-config`).
`POST /api/v1/auth/login` без капчи отвечает HTTP 400, код `4602`, `Missing captcha input`
(проверено с заведомо несуществующей тестовой почтой). Поэтому серверный вход по паролю не добавлен.
Браузерный OAuth клиента Senkuro с callback на локальном Tanuki после входа отклонён:
`redirect_uri mismatch` (ручная проверка пользователя, 2026-10-30). Для автоматического
возврата нужен зарегистрированный OAuth-клиент Tanuki с разрешённым callback;
callback клиента Senkognito отдельно не проверялся.
Один токен проверен вживую с разрешения пользователя 2026-10-30: оба GraphQL API с собственными
`app-id` узнали один аккаунт и разрешили запрос `userBookmarks`. Jar хранит токен по одному
общему адресу, чтобы смена каталога или зеркала не требовала повторного переноса.
Токен передаётся как `Authorization: Bearer …`, каталог выбирает `app-id` сайта. Аккаунт и папки — `viewer.user` и
`viewer.userBookmarkCollections`; учитываются только коллекции `entityType: MANGA`, имя берётся
из `preference.name`, если оно задано. Системные `WATCHING`, `PLANNING`, `COMPLETED`, `FAVORITED`,
`PAUSED`, `DROPPED` сопоставляются встроенным папкам; перечитывание, неизвестные статусы и свои
коллекции сохраняются отдельно. Закладки — `userBookmarks(userId:, subjectType: MANGA)` по 20
с курсором `pageInfo.endCursor` до `hasNextPage: false`. Дополнительно проверяется
`entity.applicationId`: закладки соседнего каталога пропускаются. Номер главы — `number`,
том не отдаётся (`null`), снимок тайтла разбирается тем же кодом, что у каталога.
Ошибки страниц и зацикленная пагинация не возвращают частичную библиотеку.

Источники с общим движком (Grouple, LibSocial, Chan) реализованы как **фабрика с конфигом**
(`createGroupleParser(config, ctx)`), а не через наследование — в Kotlin один класс на источник
был вынужденной мерой (KSP-аннотация `@MangaSourceParser` требует по классу на элемент enum),
в TS такого ограничения нет, а конфиги ещё и перечисляемы, что важно для реестра.

### Главная сайта (`getHome`)

Для страницы «Подборки» — блоки, которые сайт сам собирает на своей главной («Горячие новинки»,
«В тренде»). Блоки описаны статически в `info.homeSections: { id, title }[]` — id стабилен (по
нему хранится выбор пользователя, `sourceId:sectionId`), название как у сайта. `getHome()`
отдаёт ровно эти блоки в этом порядке; блок, которого на странице не нашлось, — пустой массив, а
не ошибка (`toHomeSections` в `core/home.ts`). Источник собирает главную несколькими запросами —
`fetchHomeSections`: упавший запрос даёт пустой блок, упали все — ошибка. Элементы — по
соглашениям `getList` (`chapters: null`), id совпадает с каталожным: карточка ведёт на тот же
тайтл. Блок в HTML находится по тексту заголовка (`findHomeHeading` в `core/html/home.ts`), а
не по позиции — переставленные блоки не ломают разбор.

У каждого блока есть `kind` (`new`, `trending`, `popular`, `top`, `updates` — по нему фронт
выбирает иконку вкладки) и, если внутри блока на сайте есть переключатель, `variants` —

сайт отдаёт порциями, отдельно листает `getHomeSection(id, { page, variant })` →

порцией. Проверено вживую 2026-10-13:

### HTTP-слой

Свой `HttpClient` поверх `undici.request` (не поверх Dispatcher-интерцепторов — те лежат ниже
редиректов и кук). Обязанности, которых нет в `undici.request` из коробки:

1. **Свой цикл редиректов** со сбором кук на каждом хопе — антибот-кука на промежуточном хопе
   не должна теряться.
2. **Декомпрессия** — `undici.request()`, в отличие от `fetch()`, не распаковывает тело по
   `Content-Encoding` сама.
3. **Charset** — DLE-сайты (MANGACHAN, HENCHAN, YAOICHAN, NUDEMOON) отдают **windows-1251**;
   декодирование как UTF-8 даёт кашу без единой ошибки, поэтому charset сначала сниффится из
   `Content-Type`, потом из `<meta charset>`.
4. **Классификация ошибок** каждого ответа в `ParserError` — включая антибот-эвристику
   (`core/http/classify.ts`), которая теперь смотрит на **настоящий** ответ источника, а не на
   JSON-конверт бывшего сайдкара.

**Куки — по семействам, не по процессу и не по источнику.** Общая на процесс кука протекает из
одного сайта в 22 чужих; отдельная кука на источник тоже неверна для MANGALIB/HENTAILIB/YAOILIB —
все три ходят на один хост `api.cdnlibs.org`, различаясь только заголовком `Site-Id`. Поле
`cookieScope` в дескрипторе источника решает это одной строкой.

Grouple-сеть (ReadManga/MintManga/SelfManga/SeiManga/Usagi) логинится через общий SSO-шлюз
`3.grouple.co` при старте процесса (`GROUPLE_USERNAME`/`GROUPLE_PASSWORD`, опционально — без них
источники работают анонимно), а полученная `gwt`-кука раскладывается по доменам всех источников
сети (`packages/parsers/src/sources/grouple/auth.ts`) — список доменов выводится из конфига
источников, а не хардкодится отдельно. AllHentai использует отдельный SSO-шлюз (`qawa.org`) со
своей учёткой (`ALLHENTAI_USERNAME`/`ALLHENTAI_PASSWORD`) и логинится отдельным вызовом —
общими Grouple-кредами не покрывается, но получаемая с `qawa.org` кука раскладывается по
доменам AllHentai тем же способом.

Эти учётки из env — **сервисные**: ими ходят только фоновые задачи (пробник, веер совпадений).
Пользователь читает Grouple, AllHentai и LibSocial через свой аккаунт. API кладёт его в
AsyncLocalStorage (`runWithSourceAccounts`, `core/source-accounts.ts`). `HttpClientImpl`
семейства с аккаунтом в scope берёт cookie только из jar этого аккаунта, общий jar с сервисной
сессией не видит и не пополняет. Движок Grouple входит повторно по сохранённому паролю
пользователя. LibSocial берёт токен своего сайта из `tokenStore` аккаунта вместо файла. MangaLib
и HentaiLib используют отдельные семейства аккаунтов (`mangalib`, `hentailib`): у каждого свои
пароль, токен и код из письма. `libSocialLoginSourceIds` перечисляет сайты, в которые умеем входить. Реестр отдаёт
`loginAccount` (вход в свежий jar) и `fetchLibSocialAccountName` (проверка токена) для привязки.
Платные главы LibSocial: `restricted_view` бывает только у них. Открытые аккаунту остаются с
`isPaid`, закрытые пропускаются, у тайтла ставится `hasPaidChapters`.
Платные главы REMANGA: закрытые пропускаются, купленные сервисной сессией остаются без
`isPaid` (своих аккаунтов у источника нет), у тайтла ставится `hasPaidChapters`.

### Пагинация

`core/paging.ts`: `planWindow`/`fetchPaged`/`fetchOffsetNative` без внутреннего состояния —
на каждый вызов `getList({offset, limit})` вычисляют, какие нативные страницы источника
покрывают запрошенное окно, и режут точный срез. Максимум 2 обращения наверх на страницу API
(кроме источников с нативным размером страницы ≥ лимита — там всегда 1).

### Идентификаторы

`core/uid.ts`: FNV-1a, маскированный до 53 бит. Совместимость с kotatsu не нужна (opaque id
эфемерны до релиза), но стабильность между рестартами процесса обязательна — `catalog.service.ts`
на BFF матчит соседние главы по `id`, пришедшему от клиента в более раннем запросе.

### Сеть inuko: Inkstory и PureManga

Inkstory (`inkstory.net`) и PureManga (`v1.puremanga.me`, хентай; голый `puremanga.me` отвечает 404) — сайты одной сети: общий API `api.inuko.me`, SSO `sso.inuko.me`, статика `static.inuko.me`
и одинаковая раскладка сайта (TanStack Start, SSR-состояние seroval). Движок один —
`createInukoParser(config, ctx)` в `sources/inuko/engine.ts`, сайты — конфиги `INUKO_CONFIGS`
(`sources/inuko/config.ts`): `id` и `serviceName` — значение API, которое сужает общий каталог до
одного сайта (`inkstory`, `puremanga.me` — с точкой, пишется как есть). Домен, название, тип
контента и `isAdult` — из `SOURCE_CATALOG`. Общие для сети: ключ XOR-расшифровки страниц
(`decryptionKey` в SSR главной, у обоих сайтов один), блоки главной (`INUKO_HOME_SECTION` — те же
заголовки, на PureManga в блоках бывают и карточки соседних сайтов с абсолютной ссылкой, они
отбрасываются), фильтры и сортировки. `uid` тайтлов — `generateUid(SOURCE_ID, id)`: одна и та же
книга сети у двух сайтов — разные тайтлы, uid Inkstory после выноса движка не изменились. Другие
сайты сети (`hexnovels` — новеллы, `selftoon`, `zenmanga`, `manga.ovh`) — будущие конфиги.

**18+ в списках.** Списки API скрывают от гостя взрослое: `/v2/books`, поиск и лента
`chapter-update-feed` не отдают книги `contentStatus` `EROTIC` и `PORNOGRAPHIC`
(`contentStatus=PORNOGRAPHIC` у PureManga — `[]`; из 40 популярных — 31 `SAFE` и 9 `UNSAFE`).
Тайтл по id, его главы и страницы открываются и гостю, SSR главной сайта взрослое показывает.
Разведка 2026-10-27: настройки `global-filters` (`contentStatuses`, `labelBlacklist`,
`preventUserAgentFiltering`) сайт читает и пишет только через server functions TanStack Start
(`createServerFn` с middleware сессии) — браузер к `api.inuko.me` не ходит вовсе, запросы к API
делает SSR-сервер сайта. `preventUserAgentFiltering` — поле пользователя (видно в SSR у профилей).
Чем SSR-сервер представляется API, пока не выяснено — снятие фильтра не реализовано, списки обоих
сайтов идут без 18+. См. [plans/puremanga-source.md](plans/puremanga-source.md).

### Источники вне форка

`HENTAICHAN_CC` (`hentaichan.cc`) — не порт: сайта нет в `tanuki-parsers-redo`, это отдельный
современный Next.js-фронтенд (не DLE-движок старого HENCHAN/`hentaichan.live`, несмотря на
общий бренд). Каталог на самой странице догружается клиентским React Query-запросом, а не
рендерится на сервере, поэтому источник данных — не HTML-вёрстка, а бэкенд на Directus
(`backend.hentaichan.cc`, найден через `Content-Security-Policy: connect-src` фронтенда):
полностью публичный, нетребующий авторизации REST (`/items/<collection>`), обнаруженный и
описанный вручную, а не портированный из Kotlin. Один элемент каталога — один релиз
(one-shot или отдельная переведённая глава, не вся серия целиком): live-проверка показала
`chapters: 1` у 7035 из 7036 записей.

Импорт HentaiChan (2026-10-31): вход через XChan SSO остаётся в браузере, Tanuki принимает
cookie `__Secure-better-auth.session_token` и проверяет аккаунт через
`/api/auth/get-session?disableCookieCache=true`. Лайки переносятся в «Любимое», история — в
«Читаю»; при выборе обеих папок дубли остаются в «Любимом». Списки читаются страницами через
Next.js Server Actions `getProfileLikes` / `getProfileHistory`: их текущие хеши находятся в
JS-модулях профиля, а не закреплены в парсере. `historyPage` из
`/api/manga/:id/engagement` — страница с единицы по всему релизу; по количеству страниц глав
Directus она переводится в номер главы и индекс страницы с нуля. История не становится
статистикой чтения: её даты и события не создаются. Публичные лайки, граница пагинации,
закрытая история гостя и клиент читалки проверены вживую. Полное чтение лайков, истории
и ответов с прогрессом проверено на привязанной личной сессии 2026-11-01; запись импорта
в библиотеку Tanuki этой проверкой не запускалась.

Регрессия покрыта обоими форматами — 40 и 42 символа.

Вход по паролю проверен отдельно 2026-10-31. Форма `id.xchan.one/sign-in` отправляет
`identifier`, `password`, `captchaToken` через Server Action `signInAction`: без токена
возвращается ошибка валидации, с заведомо неверным токеном — `serverError` «Проверка
\"Я не робот\" не пройдена». В форме есть Cloudflare Turnstile; проверка обязательна и на
сервере. Стандартный `POST /api/auth/sign-in/email` отвечает HTTP 400
`EMAIL_PASSWORD_DISABLED`, `/api/auth/sign-in/username` — HTTP 404.
Старый Directus `POST https://backend.hentaichan.cc/auth/login` на вымышленные почту и пароль
отвечает HTTP 401 `INVALID_CREDENTIALS`. С предоставленной пользователем учёткой вход по
почте и паролю успешно проверен: получена пара access/refresh. Однако `/users/me` возвращает
только `id`, а `/permissions/me` и авторизованный OpenAPI не открывают личные лайки и историю.
При передаче полученного Bearer в `/api/auth/get-session?disableCookieCache=true` оба сайта —
`hentaichan.cc` и `id.xchan.one` — возвращают `null`: токен Directus не является веб-сессией.
Таким образом, проверенный Directus-вход пока не даёт пути к импорту личной библиотеки;
автоматический вход по паролю не добавлен. Учётные данные и токены не сохранялись в файлы.

`SEXKOMIX2` (`sexkomix2.com`) — тоже не порт, обычная серверно-рендеренная PHP-вёрстка
(своя CMS, не DLE), обнаруженная и описанная вручную по разметке. Каталог (`li.comix`) и
пагинация (`/home/` и `/search/` с общими параметрами `sort=date|prosmotr|like&page=N`)
одинаковы для листинга и поиска. Как и NUDEMOON, один элемент каталога — один релиз
(единственная синтетическая глава на `getDetails`, без реального разбиения на главы).
Часть страниц галереи доступна только по VIP-подписке — анонимный `getPages` возвращает
столько страниц, сколько сайт отдаёт без авторизации (не всегда полный релиз), это не баг
парсера.

Разметка листинга содержит три (невалидных, задублированных) `<ul id="comix_directory">`:
VIP-промо-карусель, реальный постраничный каталог и виджет «Ещё комиксы»
(`#more_comics_directory`) — только средний из них соответствует `sort=`/`page=`, поэтому
`findCatalogList` берёт последний `<ul>` вне `#more_comics_directory` (на `/home` их два и
нужен второй, на `/search` карусели нет и нужен первый — «последний вне more_comics» верно
в обоих случаях). Внутри самого каталога один из 24 слотов `li.comix` на странице — всегда
рекламная вставка (`div.opt[data-asg-ins]` без `<a>`), поэтому фактический размер страницы
для `fetchPaged` — 23, а не 24; со значением 24 каждая страница ложно выглядела бы как
последняя и пагинация обрывалась на первой же странице.

`MULTPORN`/`MULTPORN_HENTAI` (`multporn.net`, общий движок `sources/multporn`) — тоже не порт:
не Drupal-сайт из форка, а обычная (немодифицированная) Drupal 7 Views-вёрстка, описанная
вручную. Сайт держит ~12 типов контента (Comics, Hentai manga, Cartoon/Hentai pictures, GIF,
видео, игры, ...) за одним экраном фильтров; из них модели `RawTitle → chapters → pages`
соответствуют только Comics и Hentai manga (один узел = одна законченная работа с постраничной
галереей), поэтому это два раздельных `SourceId` на одном движке и домене — остальные типы не
реализованы. `getList` без поискового запроса бьёт в `/new?type=1|3&sort_by=created` (15 строк
на нативную страницу, `fetchPaged` с `firstPage: 0` — у Drupal-пейджера страницы с нуля); с
запросом — в общесайтовый `/search`, у которого **нет** фильтра по типу контента: одна нативная
страница (всегда 20 строк) мешает комиксы с видео/играми/т.п. в одном фиде. Поэтому `parseRow`
принимает `pathPrefix` (`/comics/` или `/hentai_manga/`) и отбрасывает чужие строки, а
`fetchSearchList` не переиспользует `fetchPaged`/`fetchOffsetNative` — его эвристика «короткая
страница = конец» смотрит на _отфильтрованное_ количество и обрывалась бы на первой же странице,
как только на ней преобладает другой тип; вместо этого код листает нативные страницы и
останавливается только когда сырых (до фильтра) строк меньше 20.

Разметка деталей и листинга частично расходится по названиям Views-полей между двумя типами
(`field-category` / `field-h-category` для тегов, `field-author` / `field-author-hentai` для
автора — оба вынесены в `MultpornConfig`), но галерея страниц всегда лежит в одном и том же
`field-com-pages` независимо от типа. Сама галерея отдаётся через виджет Juicebox, чья настоящая
разметка — `<noscript>` fallback «для устройств без JS»: htmlparser2 хранит содержимое
`<noscript>` как сырой текст, а не как дочерние элементы, поэтому `<img src>` вынимаются оттуда
регэкспом, а не обычным cheerio-селектором. Каждый `src` — уменьшенный Drupal image style
(`.../styles/juicebox_medium/public/<path>?itok=...`); обрезка `styles/<name>/public/` и
`?itok=` до оригинала подтверждена вживую (оригинал ~5x тяжелее превью, оба отдают 200).
Обложка и описание берутся не из этой галереи, а из `<meta property="og:image">`/`og:description`
(модуль metatag, отдаётся на каждой странице сайта) — на самих страницы деталей нет ни капли
даты публикации, поэтому `RawChapter.uploadDate` там всегда `0` (документированный сентинел
«неизвестно»), а не пробел в парсинге.

Особенность RU-источников — **ветки переводов**: у одного тайтла на ReadManga или MangaLib
бывает несколько команд перевода со своими нумерациями глав (`RawChapter.branch`). Модель
данных и UI это учитывают с самого начала, см. [04 — Контракт API](04-api-contract.md).

## Устойчивость

Парсеры ломаются — сайты меняют вёрстку и защиту раз в несколько недель, это норма, не инцидент.
Что есть в BFF с первого дня (не изменилось после перехода на TS — то же самое просто оборачивает
прямой вызов реестра, а не HTTP-запрос к сайдкару):

- **Circuit breaker на источник** (`apps/api/src/resilience/source-health.service.ts`). 5 ошибок
  подряд → запросы к источнику не пропускаются `SOURCE_BREAKER_RESET_MS` (по умолчанию 3 минуты),
  потом идёт ровно одна пробная. Это только гейт трафика — «не долби мёртвый сайт»; состояние
  живёт в памяти процесса и теряется при рестарте.
- **Concurrency limiter на источник** — не больше N одновременных запросов к одному домену.
- **Stale-while-revalidate** в Valkey — протухший кеш лучше ошибки.
- **Живые контрактные тесты** (`packages/parsers/contract/`, ночной CI,
  `.github/workflows/parsers-nightly.yml`) — по одному проходу `getList → getDetails → getPages`
  на каждый портированный источник. Сама проверка живёт в
  `packages/parsers/src/core/source-contract.ts` (`runSourceContract`), потому что тот же путь
  чтения гоняет рантаймовый пробник в API.

  В CI токены LibSocial лежат в `mangalib.json` и `hentailib.json` (регистр совпадает с
  `SOURCE_ID`). Workflow берёт их из `LIBSOCIAL_MANGALIB_TOKEN` и `LIBSOCIAL_HENTAILIB_TOKEN`.
  Первичный вход требует кода из письма: нужно один раз выполнить
  `pnpm --filter @tanuki/parsers login:libsocial <sourceId>` и сохранить JSON из
  `data/libsocial-tokens/<sourceId>.json` в соответствующий secret environment
  `parsers-nightly`. Первый запуск может взять исходные токены из repository secrets;
  сохранённые затем environment secrets имеют приоритет. После тестов оба токена
  сохраняются обратно в environment через `GH_SECRETS_PAT`,
  в том числе при падении другого источника: refresh-токены одноразовые. Запуски workflow
  выполняются последовательно, чтобы не потратить один токен одновременно. Токены хранятся
  именно в environment: GitHub читает их при старте job, после ожидания очереди; repository
  secrets читаются ещё при постановке workflow в очередь и могут к старту устареть.

### Статус источника

Статус (`ok`/`degraded`/`down`), который видит пользователь, — отдельная от breaker'а сущность
(`apps/api/src/resilience/source-status.service.ts`). Он **липкий**: держится, пока его не сменит
явное событие, и переживает рестарт (таблица `source_health` в Postgres; пустая таблица означает
«все источники ok»). Раньше статус вычислялся прямо из breaker'а, и источник, лежащий неделю,
показывался «онлайн» через десять минут после последней ошибки.

Что двигает статус:

| Событие                                                                          | Результат  |
| -------------------------------------------------------------------------------- | ---------- |
| Открылся circuit breaker на живом трафике                                        | `degraded` |
| Упала ночная проверка                                                            | `degraded` |
| `SOURCE_PROBE_FAILURE_THRESHOLD` упавших ночей подряд (по умолч. 3)              | `down`     |
| `SOURCE_RECOVERY_SUCCESS_THRESHOLD` успешных живых запросов подряд (по умолч. 5) | `ok`       |
| Успешная ночная проверка                                                         | `ok` сразу |

Ручного сброса нет — намеренно. Кто-то нажавший «сбросить» не чинит источник: это лишь прячет
проблему до следующей ошибки, а «липкость» статуса именно в том и заключалась, чтобы такого не
происходило. Единственный способ вернуть источник в `ok` — реальный сигнал о том, что он снова
отвечает (строка выше). Ускорить эту проверку можно — `POST /sources/:id/probe` — но не обойти.

`isBroken` в `SOURCE_CATALOG` — жёсткий оверрайд поверх всего этого: такой источник всегда `down`,
пробник в него не ходит, автоматика его не трогает. Это решение человека («сайт не парсится в
принципе»), и случайный удачный запрос не должен его снимать.

### Ночная проверка (`apps/api/src/source-probe/`)

Cron-задача внутри API (`SOURCE_PROBE_CRON`, по умолчанию `0 3 * * *`) прогоняет `runSourceContract`
по всем источникам, включая `degraded` и `down`, и применяет результат к статусу. Живёт в API, а не
в GitHub Actions, хотя проверка там та же: у API есть база, куда писать статус, те же учётки и
обычный домашний IP — у раннеров GitHub адреса зашейрены и регулярно ловят антибот-403, по ним
половина источников выглядела бы лежащей, будучи живой. Прогон в CI остаётся регресс-тестом
парсеров.

Пробник ходит в парсер напрямую, **мимо кеша и мимо breaker'а**: через `guardedFetch` он получал бы
`SOURCE_UNAVAILABLE` на открытом breaker'е и не смог бы проверить ровно те источники, ради которых
нужен. Он же — единственный путь восстановления для `down`: веер поиска и матчинга такие источники
уже не опрашивает, так что живых запросов туда не приходит.

Ручной запуск — только персоналу (админ и модераторы, остальным 403): `POST /sources/probe` (все)
и `POST /sources/:id/probe` (один); на фронте — страница
«Здоровье источников» (`/sources/health`; раскладка — см.
[Таблица здоровья источников](11-ui-decisions.md#таблица-здоровья-источников)).

### Решение по антиботу

`packages/parsers/src/core/http/classify.ts` эвристически отличает антибот-челлендж
(Cloudflare/ddos-guard заголовки и тела ответа) от обычной недоступности источника и бросает
`SourceBlockedError` вместо `SourceUnavailableError` — честнее для мониторинга. В отличие от
сайдкар-версии, эта проверка теперь смотрит на **настоящий** ответ источника (сайдкар видел
только `{"error": "..."}`, в который Ktor заворачивал исключение парсера, и поэтому эвристика
практически не могла сработать).

### Grouple: авторизация

`GroupleParser` (в форке) считает, что логин требуется, если путь запроса оканчивается на
`/login`, либо приходит 404 без `gwt`-куки в jar'е — то есть любой настоящий 404 на Grouple-домене
без активной сессии тоже маскируется под ошибку авторизации. Порт (`sources/grouple/engine.ts`)
воспроизводит это поведение через HTTP-интерцептор.

Чтобы получить доступ к главам, требующим сессии (типично для MintManga/SelfManga), нужен
аккаунт на grouple.co (общий паспорт для всей сети) и `GROUPLE_USERNAME`/`GROUPLE_PASSWORD` в
`.env` — см. `.env.example`. Юридический риск скриптового логина под живым аккаунтом — см.
[09 — Правовые аспекты](09-legal.md).

AllHentai — особый случай: там 404 без сессии отдаёт не только страница логина, а весь каталог,
поэтому источник бесполезен без авторизации (`SOURCE_AUTH_REQUIRED` на любой запрос), а не
только деградирует на отдельных главах. Нужен отдельный аккаунт на `qawa.org` и
`ALLHENTAI_USERNAME`/`ALLHENTAI_PASSWORD` в `.env`.

### Desu: авторизация

Всё открыто гостю; аккаунт (семейство `desu`, `optional`, без `loginBenefits`) нужен только
импорту закладок — чтобы прочитать список именно этого человека. Вход — форма XenForo:
`POST /login/login` (`login`, `password`, `remember=1`, `cookie_check=1`, пустой `_xfToken`,
`redirect`), перед ней — `GET /login/`: с `cookie_check` запрос совсем без cookie (а jar аккаунта
создаётся пустым) отвергается до проверки пароля — «должны быть включены cookie». Неверный
пароль — 200 со страницей входа и `errorPanel` (его текст пишется в лог), принятый — редирект на
`redirect`. Признак сессии и id аккаунта — `visitor: { user_id }` на странице
(`sources/desu/auth.ts`). Истёкшая сессия при импорте с сохранённым паролем восстанавливается
повторным входом. XenForo проверяет `_xfToken` у POST только вошедших, поэтому быстрый поиск
(`POST /manga/search/`) всегда уходит гостем (`runWithSourceAccounts({})`) — от аккаунта пустой
токен не прошёл бы.

### Nude-Moon: авторизация

Каталог, страница тайтла и читалка Nude-Moon открыты гостю, а `/search` гостя редиректит на
`/error.php` (404). Вход — форма самого сайта: `POST /setuser.php` (`user_name`, `user_pass`,
`remember_me=y`), признак сессии — cookie `fusion_user` на полгода; неверный пароль её не ставит
(`sources/nudemoon/auth.ts`). Сайт в windows-1251, и `stext` он читает так же: запрос и поля формы
кодируются в cp1251 (`encodeCp1251`), запрос в UTF-8 уводит на сторонний поиск.

Поиск идёт через сессию зрителя (семейство `nudemoon`, привязка — как у Grouple). У зрителя без
аккаунта сессии нет вовсе — запрос до сайта не доходит, `SourceAuthRequiredError`; общий jar с
сервисной учёткой (`NUDEMOON_USERNAME`/`NUDEMOON_PASSWORD`) — только для фоновых задач и живых
тестов. Если сайт отверг сессию, а пароль сохранён, парсер один раз входит заново. Выдача поиска
пагинируется теми же окнами `rowstart` по 30, что `all_manga`, но в `catalogCaches` не попадает —
ключ на каждый запрос копился бы без конца.

## Тесты

Раннер — **vitest**. Два независимых слоя, отвечающих на разные вопросы:

- **Фикстурные + conformance (`packages/parsers/test/`, каждый PR).** Один параметризованный
  набор инвариантов, который обязан пройти каждый источник: `chapters === null` в списке и
  заполнены в деталях; `rating` либо `-1`, либо `0..1` (не `0..10`); `uploadDate` — миллисекунды
  или `0`; id глав уникальны и стабильны между рестартами; `RawPage.url` абсолютный.
- **Живые контрактные (`packages/parsers/contract/`, только ночной CI)** — реальные запросы к
  сайтам, `getList → getDetails → getPages` по каждому портированному источнику, с
  `allSettled`-семантикой: один мёртвый сайт не маскирует остальные.

`apps/api` тоже покрыт точечно — `common/normalize.test.ts` и `common/opaque-id.test.ts`
фиксируют сентинел-конвенции (`-1` → `null`, `0` → `null`, epoch-миллисекунды), которые обязаны
остаться неизменными независимо от того, что происходит на стороне парсеров.

## Как добавить источник

1. Найти соответствующий парсер в `tanuki-parsers-redo/src/main/kotlin/.../site/ru/`.
2. Если он — часть уже портированного движка (Grouple/LibSocial/Chan), добавить конфиг в
   `packages/parsers/src/sources/<engine>/config.ts` и обновить `RAW_TABLE` в `registry.ts`
   (`isImplemented: true`).
3. Если новый standalone-движок — создать `packages/parsers/src/sources/<id>/index.ts` с
   `create<Name>Parser(ctx): Parser`, портировать логику из Kotlin-файла один в один
   (селекторы, форматы дат, сентинелы), подключить в `registry.ts`.
4. Фикстурные тесты: записать реальный HTML/JSON в `test/fixtures/<ID>/`, добавить источник в
   параметризованный `conformance`-набор.
5. Добавить в `IMPLEMENTED_SOURCE_IDS` в `contract/live.test.ts`.
6. Если на главной сайта есть списки тайтлов — описать блоки в `info.homeSections` и реализовать
   `getHome` (см. [Главная сайта](#главная-сайта-gethome)), фикстура главной — в `test/fixtures/`.
7. Убрать/добавить источник в `DISABLED_SOURCES` в `.env.example`, если он готов к использованию.
