# 01 — Архитектура

## Принцип

Tanuki не владеет контентом. Он владеет **опытом чтения**. Любые метаданные и изображения
транзитом проходят через сервер и оседают только в кешах с TTL.

Из этого следует главное архитектурное ограничение: **чистое клиентское приложение
невозможно**. Браузер не сможет ходить на сайты-источники напрямую по четырём причинам:

1. **CORS** — ни один источник не отдаёт `Access-Control-Allow-Origin`.
2. **Хотлинк-защита картинок** — CDN источников требуют корректный `Referer` и
   `User-Agent`, которые браузер запрещает подменять из JS.
3. **Антибот-защиты** — часть источников за Cloudflare, челлендж нужно решать на сервере.
4. **Нагрузка на источники** — без общего кеша каждый пользователь бил бы по сайту сам.

Поэтому серверная часть обязательна, но её роль — **прокси и кеш**, а не база контента.

## Схема

```
┌──────────────────────────────────────────────────────────────┐
│  Браузер / PWA                                               │
│  React 19 · Mantine 9 · TanStack Query · Zustand             │
│  IndexedDB (Dexie): библиотека, история, прогресс            │
│  Cache Storage: страницы скачанных глав                      │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS, JSON + image stream
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  apps/api — BFF (NestJS 11 + Fastify 5)                      │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ CatalogModule   нормализация ответов источников        │  │
```

## Границы сервисов

### `apps/parsers` — JVM-сайдкар

Единственная его задача — превратить Kotlin-библиотеку в HTTP-сервис. Он **stateless**,
**без кеша**, **без бизнес-логики**. Тонкая обёртка: принял запрос → вызвал
`MangaParser` → отдал JSON.

Почему сайдкар, а не порт парсеров на TypeScript:

- `kotatsu-parsers-redo` покрывает **все** значимые русские источники и обновляется
  сообществом при их поломках. Переписывание — это перманентный долг сопровождения.
- Парсеры ломаются часто и не по вашей вине. Апдейт форка = `./gradlew` bump вместо
  недели реверс-инжиниринга.
- Изоляция: если парсер уронил JVM (OOM на большом каталоге), BFF остаётся живым.

Цена: второй рантайм в docker-compose и ~250 МБ RAM на JVM. Приемлемо.

### `apps/api` — BFF на TypeScript

Здесь вся логика, которая делает продукт продуктом:

- **Нормализация.** Разные источники дают разную полноту данных. BFF приводит их к
  единой доменной модели (см. [04 — Контракт API](04-api-contract.md)).
- **Кеширование.** Каталог — 15 минут, детали тайтла — 1 час, список страниц — 6 часов,
  список источников — сутки. Ключ включает `sourceId`, чтобы инвалидация была точечной.
- **Image proxy.** Единственный эндпоинт, через который идут байты картинок. Подставляет
  `Referer` источника, стримит без буферизации целиком в память, опционально
  переупаковывает в WebP/AVIF через `sharp` и режет по ширине вьюпорта.
- **Устойчивость.** Rate limiter на каждый источник, circuit breaker, вежливые таймауты.
  Агрегатор, который дудосит источник, убивает и источник, и себя.
- **Агрегация.** Поиск сразу по нескольким источникам, дедупликация одинаковых тайтлов,
  склейка глав из разных переводов.

### `apps/web` — PWA

Vite-приложение. Полностью клиентский роутинг, никакого SSR. SEO для агрегатора
контента — не цель (и, откровенно, нежелателен, см. [09 — Правовые аспекты](09-legal.md)).

## Ключевые потоки

### Открытие главы

```
1. web → GET /api/v1/manga/:sourceId/:mangaId/chapters/:chapterId/pages
2. api: проверяет Valkey (ключ pages:sourceId:chapterId, TTL 6ч)
3. промах → api → GET parsers:8080/sources/:id/pages?chapterUrl=...
4. parsers → сайт-источник → HTML/JSON → список Page
5. api нормализует: каждый page.url переписывается в /api/v1/img?u=<signed>
6. web получает список из N проксированных URL
7. <img> тянет /api/v1/img → api стримит байты с источника с нужным Referer
```

Подпись `u` обязательна: без неё эндпоинт превращается в открытый прокси, через который
кто угодно погонит любой трафик. HMAC от `(url, sourceId, exp)` с серверным секретом.

### Офлайн-чтение

```
1. Пользователь жмёт «Скачать главу»
2. web получает список страниц как обычно
3. Service worker последовательно фетчит все /api/v1/img и кладёт в Cache Storage
   (отдельный кеш `tanuki-offline-v1`, не подпадает под LRU-вытеснение)
4. Метаданные главы пишутся в IndexedDB со статусом `downloaded`
5. При открытии главы офлайн SW отдаёт картинки из кеша, а метаданные — из Dexie
```

## Что осознанно НЕ делаем

- **Не храним изображения на диске сервера.** Только стриминг и HTTP-кеш на CDN-уровне.
- **Не делаем свой поиск/индекс по всем источникам.** Это превратило бы прокси в базу.
- **Не делаем SSR.** Усложняет, ничего не даёт, повышает правовые риски.
- **Не поддерживаем «свои» загрузки пользователей.** Это другой продукт.
